# 03 路径与命名规范

> 状态：评审中
> Owner：架构师
> 最后更新：2026-10-05
> 关联：`Story/04_架构/01_架构现状核查.md`（第 7 章现状对照）、`Story/04_架构/02_目标结构蓝图.md`、`Story/README.md`（第 3 章配置表约定）

## 0. 本规范要消灭的那个 bug

`Scripts/Runtime/Path&Type/GlobalPath.cs` 里混着**三种互不兼容的路径基准**，而 `data_JsonPathToRead` 恰好写错了基准之外的部分（少了 `Data/`），导致运行时读配置永远失败（`01_架构现状核查.md` C1，Unity 实测已确证）。

**根因不是笔误，是缺少「基准」这个概念。** 本规范把所有路径按**消费者**分成三种基准，每种基准只允许一种写法。

## 1. 三种路径基准（核心规则）

| 基准 | 谁来消费 | 起点 | 正确写法 | 错误写法 |
| --- | --- | --- | --- | --- |
| **① `Assets/` 开头** | `AssetDatabase.*`、编辑器工具（`Directory`/`File` 直读工程资产） | 工程根 | `Assets/Resources/UIPanels` | `UIPanels`、`Resources/UIPanels` |
| **② `Resources/` 之后** | `Resources.Load` / `Resources.LoadAsync` | `Assets/Resources/` | `Data/Json/Runtime/TestTableConfig` | `Assets/Resources/Data/...`、`Resources/Data/...` |
| **③ `Application.dataPath` 相对** | `File`/`Directory`/`FileInfo` 运行时与导出 IO | 编辑器 = `<工程>/Assets`；打包 = `<Build>_Data` | `Excel/Chaos_excel/` | `Assets/Excel/...`、`Resources/...` |
| **④ `Application.persistentDataPath` 相对** | **唯一可写的存档 IO** | 平台可写目录 | `Config/settings.json` | 任何 `Application.dataPath` 下的写操作 |

补充两条：

- **②永远不带扩展名**（`Resources.Load` 不认扩展名）。
- **`Resources/` 目录下不允许出现「运行时会写」的文件**（`Resources` 会被打进包体，只读）。

> 现实对照（现状为什么容易错）：同一个物理文件 `Assets/Resources/Data/Json/Runtime/TestTableConfig.json`
> **导出时**要用基准③写成 `Resources/Data/Json/Runtime/`（`data_JsonPath`），
> **运行时**要用基准②写成 `Data/Json/Runtime/`（`data_JsonPathToRead`）。
> 两个常量长得像但基准不同 —— 这就是 C1 的温床。规范要求：**这类「同一个文件的读写两个键」必须在常量名与注释里同时写明基准。**

### 2.2 目标写法（推荐重排为四组，并给每个常量标注基准）

```csharp
public static class GlobalPath
{
    // ── ① AssetDatabase / 编辑器工具用：一律 "Assets/..." 开头 ──
    public static readonly string[] ui_PanelPrefabSearchPaths = { "Assets/Resources/UIPanels" };
    public const string ui_DefaultLocalizationConfigPath = "Assets/Data/Localization/Sub_LD/SettingLocalizationConfig.asset";

    // ── ② Resources.Load 用：基准是 Assets/Resources/，不带扩展名 ──
    public const string res_PanelPath        = "UIPanels/";
    public const string res_KeyIconMapPath   = "Data/Input/KeyIconMap";
    // 【修复 C1】只读配置：基准② → "Data/Json/Runtime/"
    public const string res_ConfigJsonDir    = "Data/Json/Runtime/";

    // ── ③ 导出器写文件用：基准是 Application.dataPath ──
    public const string data_ExcelPath       = "Excel/Chaos_excel/";
    public const string data_JsonOutDir      = "Resources/Data/Json/Runtime/";
    public const string data_DefaultOutDir   = "Resources/Data/Default/";      // 新档初值（新）
    public const string data_ExcelClassPath  = "Scripts/Runtime/MVP/Model/ConfigData/";
    public const string data_ExcelModelPath  = "Scripts/Runtime/MVP/Model/ModelData/";
    public const string data_RecordPath      = "Data/Records/";                // 仅编辑器期存档

    // ── ④ 运行时存档用：基准是 Application.persistentDataPath ──
    public const string save_RecordDir       = "Records/";
}
```

要点：
- **命名前缀即基准**：`ui_` = ①，`res_` = ②，`data_` = ③（导出/工程内），`save_` = ④（持久化）。看到前缀就知道该用什么 API，不用回查。
- **读写分离命名**：同一个物理位置若同时有「写键」和「读键」，两个常量名必须能一眼区分（如 `data_JsonOutDir` / `res_ConfigJsonDir`），并各自注明基准。
- **`data_JsonPathToRead` 这个名字保留亦可**，但语义应改为「基准②，值为 `Data/Json/Runtime/`」。**不要在修复时顺手改成基准①或③** —— 那是把错误从一处搬到另一处。

### 2.3 生成物目录与存档目录必须分离

现状：`data_RecordPath = "Data/Records/"` 被导出器（`ConfigManager.cs:221`）与存档器（`Recorder.cs:43`）**同时使用**，且该目录被 git 跟踪。三种写入方（导出器、Recorder、新档初值）挤在一个目录 → 生成物覆盖玩家存档、跑一次导出就脏工作区。

目标：

| 用途 | 目录 | 基准 | 谁写 | git |
| --- | --- | --- | --- | --- |
| 只读配置 | `Resources/Data/Json/Runtime/` | ③ | 仅导出器 | 生成物，可提交 |
| 新档初值 | `Resources/Data/Default/` | ③ | 仅导出器 | 生成物，可提交 |
| 编辑期存档 | `Data/Records/` | ③ | 仅 `Recorder`（编辑器） | **必须加进 `.gitignore`** |
| 打包后存档 | `Application.persistentDataPath/Records/` | ④ | 仅 `Recorder`（运行时） | 不在工程内 |

## 3. 资源加载路径前缀速查

| 场景 | 写法示例 | 陷阱 |
| --- | --- | --- |
| `ResManager.Load<TextAsset>("Data/Json/Runtime/TestTableConfig")` | 基准② | 不带 `.json`；不带 `Assets/`/`Resources/` |
| `AssetDatabase.FindAssets(..., new[]{ "Assets/Resources/UIPanels" })` | 基准① | 必须带 `Assets/` |
| `new FileInfo(Application.dataPath + "/Excel/Chaos_excel/TestTable_测试表.xlsx")` | 基准③ | 拼接时**避免双斜杠**（现 `ImpTableTest.cs:16-17` 会产生 `Chaos_excel//TestTable...`，Windows 下无害但应修） |
| `Path.Combine(Application.persistentDataPath, "Config", "settings.json")` | 基准④ | 正确范例见 `SettingsManager.cs:46-49`，用 `Path.Combine` 而非字符串拼 |
| 面板预制体 | `Resources/UIPanels/{PanelType}.prefab` | 文件名**必须** == `PanelType` 枚举成员名（`UIManager.cs:173` 用 `ToString()` 拼） |

**禁止**：在任何地方出现 `Resources.Load` + `Assets/` 前缀；出现 `File` IO + `Resources/` 前缀；出现运行时对 `Application.dataPath` 的**写**操作。

## 4. 类名 / 文件名 / 命名空间规范

### 4.1 文件名与类名

- **一个文件一个 public 类型，文件名 == 类型名**（例外：`{表名}Config.cs` / `{表名}Data.cs` 见第 5 章；同一文件的嵌套/私有辅助类允许）。
- 既有文件名后缀语义（已形成惯例，沿用）：

| 后缀 | 含义 | 所在层 | 例 |
| --- | --- | --- | --- |
| `*Config` | **生成**的只读配置 DTO | `MVP/Model/ConfigData/` | `TestTableConfig.cs` |
| `*Data` | **生成**的可写存档 DTO | `MVP/Model/ModelData/` | `TestTableData.cs` |
| `*Model` | **手写**运行时 Model（有生命周期、实现 `IModel`） | `MVP/Model/<System>/` | `QuestModel.cs` |
| `I*View` | View 抽象接口（Presenter 只认它） | `MVP/Presenter/<System>/` | `IQuestView.cs` |
| `*Presenter` | 手写 Presenter，**不继承 MonoBehaviour** | `MVP/Presenter/<System>/` | `QuestPresenter.cs` |
| `*Panel` | 面板，继承 `BasePanel` | `MVP/View/<System>/` | `QuestPanel.cs` |
| `*Page` | 副设置列表的「一页」，继承 `SettingsPageBase` | `MVP/View/SettingsPage/` | `AudioSettingsPage.cs` |
| `*Cell` / `*Row` | 列表单元 / 行控件 | `MVP/View/`、`GameBase/SettingRows/` | `RecordCell.cs`、`SettingRow_Slider.cs` |
| `*Manager` | **跨系统全局服务**，继承 `SingletonBase<T>` | `GameBase/<Xxx>Manager/` | `UIManager.cs` |
| `*Tool` / `*Window` | 编辑器工具 | `Scripts/Editor/` | `IconAtlasBuilder.cs` |
| `*VM` | 仅供 Presenter→View 传递的展示数据（值类型） | `MVP/Presenter/<System>/` | `QuestItemVM.cs` |

- **保留后缀**：`Config`、`Data` 两个后缀**专供生成物**，手写类**禁止**使用（否则会在导出时被同名生成物覆盖，见第 6 章）。
- 禁止命名：`Test`/`Temp`/`New`/`Manager2`/`xxxCopy` 出现在 `Scripts/Runtime/`（正式树）下；测试代码一律放 `Scripts/Runtime/GameTest/` 之外的**独立测试场景**，或直接删。
- 私有字段沿用 `_camelCase`（工程现状一致）；常量沿用 `PascalCase` 或既有 `前缀_ + 含义` 风格（`GlobalPath` 的 `res_`/`data_`/`ui_`）。

### 4.2 命名空间

现状：**绝大多数类型在全局命名空间**（`SettingsManager`、`UIManager`、`BasePanel`、`ConfigLoader`…），仅 `DialogueSystem`、`LocalizationSystem`、`ChaosDebug`、`TangLaoShi`（死代码）有命名空间。

规范（**增量式，不做全量搬迁**）：

- **不要求**把既有全局类型迁进命名空间 —— 收益低、冲突面大（`BasePanel`/`UIManager` 被 prefab 序列化引用）。
- **新增** MVP 三层的代码，统一用：

```
Chaos.MVP.Model.<System>
Chaos.MVP.Presenter.<System>
Chaos.MVP.View.<System>
```

- 新增 `GameBase/` 服务用 `Chaos.GameBase`。
- 配置/存档基础设施用 `Chaos.Config`。
- 已存在命名空间的模块（`ChaosDebug`、`LocalizationSystem`、`DialogueSystem`）保持不动。
- **禁止**新增 `TangLaoShi` 这类与项目无关的命名空间（现为死代码，应随目录一起删）。
- ⚠ 若采用命名空间，**生成物怎么办**：导出器目前生成的是全局命名空间类（`ConfigManager.cs:148-170` 不写 namespace），而 `Resources/Data/Json/` 的 json key 与字段名无关、与类型名无关，**改命名空间不影响 json**，但会影响 `JsonUtility.FromJson<DataList<T>>` 的调用点（只影响编译期类型引用）。建议：**生成物保持全局命名空间**（零迁移成本），手写代码用命名空间并通过 `using` 引用。这是刻意的例外，写在这里以免后人「顺手统一」。

## 5. 配置表名 → 类名 / Json 名 推导规则

### 5.1 推导链

```
文件名:   QuestConfig_任务表.xlsx
             │  GlobalPath.data_ExcelPath 下的 *.xlsx
             ▼
       GetFileName() = 文件名.Split('_')[0]        // ConfigManager.cs:237-241
             │
        base = "QuestConfig"
             │
    ┌────────┴────────┐
    │ mode=Config     │ mode=Data
    ▼                 ▼
类: QuestConfigConfig 类: QuestConfigData        // ConfigManager.cs:152  ← 注意："{base}{mode}"
Json: QuestConfigConfig.json   Json: QuestConfigData.record/.json
目录: MVP/Model/ConfigData/    目录: MVP/Model/ModelData/
```

### 5.2 必须遵守的三条

1. **`_` 前的英文段是唯一标识**：必须 (a) 合法 C# 标识符、(b) 全工程唯一、(c) **不含下划线**。因为 `Split('_')[0]` 只取第一段。
2. **`_` 之后是给人看的中文说明**，随便写，不影响导出。
3. **注意类名会拼上 `Config`/`Data` 后缀** —— 所以表名不要自己再带后缀。`TestTable_测试表.xlsx` → `TestTableConfig` / `TestTableData` ✅；若写成 `TestTableConfig_测试表.xlsx` 会得到 `TestTableConfigConfig` ❌。

### 5.3 已知缺陷与规避（导出器未做查重）

`GetFileName` 只取第一段且**不检查重名**（`ConfigManager.cs:237-241`）：`A_B.xlsx` 与 `A_C.xlsx` 会得到同一个类名与同一个 json 名，**后者静默覆盖前者，无任何日志**。

规避规则（在导出器补查重之前，由策划+架构师共同守）：

- [ ] 新增表前，`Excel/Chaos_excel/` 下**下划线前的英文段必须全局唯一**。
- [ ] 表名不得与既有 C# 类型重名（生成物是全局命名空间！例如表名叫 `Settings` 会与设置系统冲突）。
- [ ] 建议表名自带模块前缀：`QuestConfig_`、`ItemConfig_`、`SkillConfig_`。

### 5.4 7 行表头（修正版 —— 以代码为准）

| 行 | 用途 | 代码消费点 | 说明 |
| --- | --- | --- | --- |
| 1 | 表名（人工查看） | 不读 | —— |
| 2 | 是否读取 / IsConfig | **不读**（未实现） | 填了无效，建议留空或删除该行概念 |
| 3 | 中文备注 | `remarkIndex=3`（`:36`） | 生成字段行尾注释 |
| 4 | 英文属性名 | `propertyIndex=4`（`:40`） | **不可为空，唯一强校验**（`:265-268` 抛异常） |
| 5 | client / both / server | `endIndex=5`（`:44`） | **真实生效**：`server` 列被类与 json 同时剔除（`:160-161,191`）。⚠ 留空会导致「类有字段、json 无 key」 |
| 6 | 类型 | `typeIndex=6`（`:48`） | 见 5.5 白名单 |
| 7 起 | **正式数据**（第一行也是数据！） | `valueIndex=7`（`:52`）、`:296-297` | **不存在「示例行」**，第 7 行会被导出 |

### 5.5 类型白名单（真实行为）

| 第 6 行填 | 导出器行为 | 结果 |
| --- | --- | --- |
| `int` `uint` `long` `ulong` `float` `double` `string` | 正常 | ✅ 可用（**推荐只用这 7 个**） |
| `int32` `int64` `long long` | `Convert` **接受**（`:330-347`），但把类型原样拼进字段（`:166`） | ❌ 生成 `public int32 x;` / `public long long x;` → **编译不过** |
| `bool` `enum` `DateTime` 及其他 | `Convert` 走 `default` → **导出期直接抛异常**（`:357-358`） | ❌ 导出失败 |
| 空 | 同上一行（抛异常） | ❌ |

> 结论：**只用 `int` `uint` `long` `ulong` `float` `double` `string`**。`Story/README.md:57` 的结论正确，但它写的原因是「会导出失败」—— 实际 `int32`/`int64`/`long long` 是「导出成功、编译失败」，排查方向不同。

## 6. 生成物与手写物分离规则

### 6.1 目录级隔离（硬规则）

| 目录 | 只允许 | 禁止 |
| --- | --- | --- |
| `MVP/Model/ConfigData/` | 导出器生成的 `*Config.cs` | 任何手写文件（包括 `partial` 补充） |
| `MVP/Model/ModelData/` | 导出器生成的 `*Data.cs` | 同上 |
| `Resources/Data/Json/Runtime/` | 导出器生成的 `*.json` | 手改、运行时写入 |
| `Resources/Data/Default/` | 导出器生成的新档初值 | 同上 |

### 6.2 为什么用「后缀 + 目录」而不是 `partial`

`partial` 能让「生成物 + 手写补充」合并在一个类里，但本项目**不采用**，理由：

1. 生成物的目录是自动化的；一旦允许 `partial`，手写文件就会出现在生成物目录里，**无法再用「目录里有没有手写文件」做违规检测**。
2. 生成的 DTO 是**纯字段容器**，给它们加行为本身就是分层错误（行为属于 Model/`<System>/`）。
3. `partial` 会让人误以为「改生成物没问题」，而导出器会**删除并重写**整个文件（`FileUtil.cs:52-56`）—— 只要头注释不是 `partial`，编译立刻失败；若是 `partial` 则会静默丢掉一部分语义，更难查。

**替代做法**：需要「表读取 / 索引 / 便捷访问」时，在 `MVP/Model/<System>/` 下手写一个包装类：

```csharp
// MVP/Model/Quest/QuestConfigTable.cs —— 手写，不属于生成物
public sealed class QuestConfigTable
{
    private readonly Dictionary<uint, QuestConfigConfig> _byId;
    public QuestConfigTable(DataList<QuestConfigConfig> data) { /* 建索引 */ }
    public QuestConfigConfig Get(uint id) { /* 查表，缺失时报错 */ }
}
```

这样：生成物永远干净；查表逻辑可单测；导出重跑不影响任何手写代码。

### 6.3 生成器必须写入的文件头（规范要求）

`ConfigManager.cs:148-152` 的模板**必须**改为（修复 C4）：

```csharp
// <auto-generated>
// 本文件由 Excel 导出工具生成（Tool/Excel/Export Configs|Models）。
// 请勿手改：下次导出会整文件覆盖。要加逻辑请在 MVP/Model/<System>/ 下另建包装类。
// 源表：Excel/Chaos_excel/{源文件名}.xlsx
// </auto-generated>
```

并**删掉**那行已经失效的模板注释（`//用于{fileName}Model类进行持久化的数据类` —— 它引用的 `{表名}Model` 类型从来不存在，见 `TestTableData.cs:4`）。

配套的自动化检查（建议加入 CI 或编辑器脚本）：
- 在 `ConfigData/`、`ModelData/`、`Resources/Data/Json/`、`Resources/Data/Default/` 下，任何**不以 `<auto-generated>` 开头**的 `.cs` 都视为违规并报错。

### 6.4 `.gitignore`

`Assets/Data/Records/` 是**运行时/编辑期存档**，必须加入根 `.gitignore`（现状被跟踪，见 `01_架构现状核查.md` R8）。生成物（`Resources/Data/**`）应提交，作为「表已被导过」的证据。

## 7. 面板 / 预制体 / 事件 命名

| 对象 | 规则 | 依据 |
