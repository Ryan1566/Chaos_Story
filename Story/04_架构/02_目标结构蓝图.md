## 0. 本蓝图要解决的问题

`01_架构现状核查.md` 的结论是：框架（Manager 层）成熟，UI 框架成熟，但 **M 层不存在、P 层为空、配置读路径是死的、存档不可用于打包**。蓝图要给出的是**「以后每加一个系统，文件放哪、叫什么、谁负责创建和销毁」的确定性答案**，而不是抽象原则。

四条设计约束（按优先级）：

1. **零成本接入**：新增一个玩法系统不应要求改动框架层代码（除枚举/常量这类注册点）。
2. **单一入口**：每种数据只有一个读取入口、一个写入入口。绝不允许出现第二个「读 Json 的类」。
3. **可静态判定归属**：放哪个目录不看个人判断，看「它会不会被运行时改写」「会不会出现在 prefab 上」两个问题。
4. **生成物与手写物物理隔离**：生成物所在目录**不允许**出现手写文件；手写文件所在目录**不允许**被导出器写入。

### 1.1 关键取舍说明

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| `ConfigData/` + `ModelData/` 要不要改名成 docx 建议的 `Config/`+`Data/` | **不改名** | 两个 `GlobalPath` 常量与导出器都已指向现名，改名收益（少了 4 个字）远小于「改常量 + 改导出器 + 重导一次表」的成本与风险。保持现名，靠文档约束语义。 |
| 导出器留不留 `Runtime/` | **必须迁到 `Scripts/Editor/`** | 现 `ConfigManager.cs:9` 的 `using UnityEditor` 是出包 P0；迁进 `Editor/` 后此类问题从机制上不可能再发生。 |
| `Data/Records/` 留不留 | **留，但只做「编辑器期存档」** | `Recorder` 在编辑器下需要落点；打包后一律走 `persistentDataPath`。**导出器不得再往这里写**（改往 `Resources/Data/Default/`）。 |
| `Resources/Data/Default/` 新目录 | **新增** | 把「生成的新档初值」与「玩家存档」彻底分开，消除 C5（同一目录三种写入方）。 |
| `Model/` 下要不要按 `<System>/` 分子目录 | **要** | 否则 8 个系统的 Model 平铺在一个目录里，与 `ConfigData/`/`ModelData/` 混在一起，无法靠目录反推职责。 |

## 2. MVP 三层各自装什么

| 层 | 目录 | 装什么 | 不装什么 | 判定问句 |
| --- | --- | --- | --- | --- |
| **Model** | `MVP/Model/<System>/`（手写）+ `ConfigData/`、`ModelData/`（生成） | 状态 + 业务规则 + 变化通知（事件）。有生命周期（Init/Dispose），实现 `IModel`。生成的纯字段 DTO 放在两个生成物目录，**不实现 `IModel`** | 不引用 `UnityEngine.UI`、不碰 prefab、不写存档路径（交给 `Recorder`）、不直接调 `UIManager` | 「它会被运行时改写吗 / 它有生命周期吗」 |
| **Presenter** | `MVP/Presenter/<System>/` | 把 View 的意图翻译成 Model 调用；把 Model 的变化翻译成 View 更新。**不继承 MonoBehaviour**（纯 C# 类）。只认识 `I<System>View` 接口，不认识具体面板类 | 不碰 `Transform`/`Button`/`TextMeshPro`、不 `Resources.Load`、不写 `PlayerPrefs` | 「它是不是在给两边做翻译」 |
| **View** | `MVP/View/<System>/` | 面板 / 页 / 行控件。继承 `BasePanel`，实现 `I<System>View`。**只显示、只采集输入**，不知道字段名对应的数据从哪来 | 不直接 `SettingsManager.Instance` / 不直接 `Recorder` / 不存业务状态 | 「它会不会被挂到 prefab 上」 |

> 与现状的最大差别：**View 不再直接摸 Manager 单例**，而是通过构造函数注入的 `I<System>View` 与 Presenter 对话。边界一个例外：`SettingsPageBase` / `SettingRow_*` 这套已经很好的「行不认识字段」机制，保持不动，只在 P 层落地时把 `SettingsManager.Instance` 换成注入的 `ISettingsModel`（见 `04_MVP契约与落地路线.md` 阶段 P3）。

## 3. 新文件落位规则（决策树）

```
要新增一个类型，按顺序问：
1. 它是 Excel 导出的吗？
   ├─ 是 → 只读常量 → MVP/Model/ConfigData/       （生成，勿手改）
   │        可写存档 → MVP/Model/ModelData/        （生成，勿手改）
   └─ 否 ↓
2. 它会出现在 prefab / 场景物体上吗？
   ├─ 是 → MVP/View/<System>/
   └─ 否 ↓
3. 它有生命周期（订阅事件 / 缓存 / 需要释放）吗？
   ├─ 是 → MVP/Model/<System>/，并实现 IModel，由 ModelHub 管创建与释放
   └─ 否 → 它是 DTO / 值类型 → 与它所属的 Model 同目录，实现 IModel 是错的
4. 它是「把 View 与 Model 对接」的那层吗？
   ├─ 是 → MVP/Presenter/<System>/
   └─ 否 ↓
5. 它是跨系统、全局唯一、其他系统也要用的服务吗？
   ├─ 是 → GameBase/<XxxManager>/，继承 SingletonBase<T>，由 Entry 显式 Init
   └─ 否 → 它就是上一条的 Model，不要升级成 Manager
6. 它需要引用 Sprite / AudioClip / GameObject / Color 吗？
   └─ 是 → 只能是 ScriptableObject 资产，放 Resources/ 或 Data/，由人在 Inspector 摆
            —— 绝不能作为 Excel 导出目标（Excel 只产出 int/uint/long/ulong/float/double/string）
```

**一条硬规则**：`Model/ConfigData/`、`Model/ModelData/`、`Resources/Data/Json/`、`Resources/Data/Default/` 四个目录**永远只由导出器写入**。任何人在这些目录下看到手写文件，都是架构违规。

## 6. 明确「不做」的清单（防过度设计）

1. **不引入 DI 容器 / 第三方 MVP 框架**。构造函数注入足够，工程规模不需要。
2. **不给每个系统建 Manager**。只有「跨场景 + 全局唯一 + 多系统共用」才升 `GameBase/`。任务系统的规则放 `QuestModel`，不放 `QuestManager`。
3. **不重命名 `ConfigData/`、`ModelData/`**（见 1.1）。
4. **不动 `SettingRows/` 与 `SettingsPageBase`** —— 现存的「行不认识字段 + 页声明绑定」机制是本工程最健康的一层，只在其上包一层 Presenter（P3），不重写。
5. **不为了 MVP 而 MVP**：如果一个系统只有「读一张配置表 + 显示列表」，允许省略 Presenter，由 View 直接持有 Model（此时必须在 P 层目录留一个空的 `README` 说明为何省略）。禁止的是「View 直接摸 GameBase 单例」。

## 7. 蓝图验收标准（程序可据此自查）

- [ ] 新增系统的文件全部落在上表 15 个路径族内，没有落在 `GameBase/` 之外的框架目录。
- [ ] `MVP/Model/ConfigData/`、`MVP/Model/ModelData/`、`Resources/Data/Json/`、`Resources/Data/Default/` 内没有任何手写文件。
- [ ] `MVP/Presenter/` 下的类**不继承** MonoBehaviour，且不 `using UnityEngine.UI`。
- [ ] `MVP/View/` 下的类不出现 `Recorder`、不出现 `ConfigRepository.Instance`（配置经构造函数传入）。
- [ ] 新增面板已在 `PanelType.cs` 注册，且 `Resources/UIPanels/{名}.prefab` 存在，Play 时 `UIManager.OnInit` 无「缺预制体」告警。
- [ ] 生成的存档 DTO 不实现 `IModel`；运行时 Model 实现了 `IModel` 且由 `ModelHub` 创建/释放。
