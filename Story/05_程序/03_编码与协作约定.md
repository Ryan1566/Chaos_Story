## 0. 这份文档怎么用

这是**程序侧的操作规范**。任何一次改码（含 Lead 与其它成员代改）都必须先过一遍本文。
每条规范都写成 **「规则 → 为什么（真实证据）→ 怎么做（可直接复制的命令）」**，不写空话。

**违规代价排序**（越大越痛）：

| 级别 | 事故 | 发生概率 |
| --- | --- | --- |
| 🔴 高 | 改 GBK 的 `.cs` 把整个文件的中文注释变成乱码，diff 变成几千行 | 很高（`Scripts/` 下 37/91 个文件是 GBK） |
| 🔴 高 | 手改生成物，下次导出被静默覆盖，白干 | 中 |
| 🟠 中 | 误用 `EventCenter` / `PauseSound` → 编译直接报错 | 低（编译器会挡） |
| 🟠 中 | 误用 `TangLaoShi.UIManager` / `TangLaoShi.BasePanel` → **只出警告、静默失效** | 中 |
| 🟠 中 | 在 `Scripts/Runtime/` 里写 `UnityEditor` → 编辑器能跑、**打包失败** | 中 |
| 🟡 低 | `.meta` 丢失/重复 → Unity 重新生成 GUID，引用全断 | 低 |
| 🟡 低 | 新增 `.cs` 不写 `namespace`，与既有全局命名空间风格一致但易冲突 | 中 |

## 1. 【🔴 最高优先级】混合编码：改 `.cs` 前必须先确认编码

### 1.2 规则

1. **不要用通用文本编辑器（含 `read`/`write` 类工具、VS Code 默认设置、记事本）直接改 GBK 文件。**
   `read` 工具读 GBK 文件会报 `invalid UTF-8`；即使某些工具"能读"，写回时默认 UTF-8
   会把**整个文件的中文注释变成乱码**。
2. **改前先判定编码，改后按原编码写回。**
3. **不确定就查前 3 字节**：`EF BB BF` = UTF-8 BOM。
4. **纯 ASCII 的 6 个文件随便改**（但保持 ASCII，别引入中文，否则要重新决定编码）。

### 1.3 可直接复制的命令

**① 判定单个文件的编码**

```powershell
$p = "Scripts\Runtime\GameBase\ConfigManager\Config\ConfigManager.cs"
$b = [System.IO.File]::ReadAllBytes((Resolve-Path $p))
if ($b.Length -ge 3 -and $b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF) { "UTF-8 带 BOM" }
else {
  try { $u = New-Object System.Text.UTF8Encoding($false, $true); [void]$u.GetString($b); "UTF-8 无 BOM" }
  catch { "GBK (936)" }
}
```

**② 读 GBK 文件（`read` 工具读不了 GBK）**

```powershell
$p = "Scripts\Runtime\Path&Type\GlobalPath.cs"
$b = [System.IO.File]::ReadAllBytes((Resolve-Path $p))
[System.Text.Encoding]::GetEncoding(936).GetString($b)
```

**③ 写回 GBK 文件（保持原编码，这是关键）**

```powershell
$p = "Scripts\Runtime\Path&Type\GlobalPath.cs"
$b = [System.IO.File]::ReadAllBytes((Resolve-Path $p))
$text = [System.Text.Encoding]::GetEncoding(936).GetString($b)
$text = $text.Replace("旧内容", "新内容")
[System.IO.File]::WriteAllText((Resolve-Path $p), $text, [System.Text.Encoding]::GetEncoding(936))
```

> ⚠ `[System.IO.File]::WriteAllText` 的第三个参数**必须显式给** `Encoding.GetEncoding(936)`。
> 不传就按 UTF-8 写，中文注释当场变乱码。
> ⚠ **不要**用 `Set-Content` / `Out-File`，它们会加 BOM 或换行转换。

**④ 写回 UTF-8 BOM 文件**

```powershell
$p = "Scripts\Runtime\MVP\View\SettingPanel.cs"
$text = [System.IO.File]::ReadAllText((Resolve-Path $p), [System.Text.Encoding]::UTF8)
$text = $text.Replace("旧内容", "新内容")
[System.IO.File]::WriteAllText((Resolve-Path $p), $text, (New-Object System.Text.UTF8Encoding($true)))   # $true = 带 BOM
```

**⑤ 改完必须自检 diff 只动了你预期的行**

```powershell
cd "D:\Unity Projects\Project_Chaos"
git diff --stat -- "Assets/Scripts/**/*.cs"
git diff -- "Assets/Scripts/你要改的文件.cs"
```
若看到"整个文件被替换"（`+`/`-` 行数接近文件总行数且内容看似相同）→ **编码被改了，立即回滚**：
```powershell
git checkout -- "Assets/Scripts/你的文件.cs"
```

**⑥ （推荐）先把全部脚本镜像成 UTF-8 到临时目录，用 `read`/`grep` 工具审查，再决定怎么改**

```powershell
$src = "D:\Unity Projects\Project_Chaos\Assets\Scripts"
$dst = Join-Path $env:TEMP "chaos_utf8"
New-Item -ItemType Directory -Path $dst -Force | Out-Null
Get-ChildItem -Recurse -File -Path $src -Filter *.cs | ForEach-Object {
  $rel  = $_.FullName.Substring($src.Length+1)
  $out  = Join-Path $dst $rel
  New-Item -ItemType Directory -Path (Split-Path $out) -Force | Out-Null
  $b = [System.IO.File]::ReadAllBytes($_.FullName)
  $enc = "UTF8"
  if (-not ($b.Length -ge 3 -and $b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF)) {
    try { (New-Object System.Text.UTF8Encoding($false,$true)).GetString($b) | Out-Null }
    catch { $enc = "GBK" }
  }
  $t = if ($enc -eq "GBK") { [System.Text.Encoding]::GetEncoding(936).GetString($b) } else { [System.Text.Encoding]::UTF8.GetString($b) }
  [System.IO.File]::WriteAllText($out, $t, (New-Object System.Text.UTF8Encoding($false)))
}
```
> **镜像目录必须放在 `Assets/` 之外**（如 `%TEMP%`），否则 Unity 会把镜像也当资产导入，
> 产生成百上千个 `.meta` 和重复类定义 → 编译报错 CS0101。

## 2. 【🔴】生成物禁改

### 2.1 哪些是生成物

| 路径 | 生成者 | 规则 |
| --- | --- | --- |
| `Scripts/Runtime/MVP/Model/ConfigData/*.cs` | `ConfigManager`（Config 模式） | **禁止手改** |
| `Scripts/Runtime/MVP/Model/ModelData/*.cs` | `ConfigManager`（Data 模式） | **禁止手改** |
| `Resources/Data/Json/**` | `ConfigManager`（Config 模式） | **禁止手改** |
| `Data/Records/*.record` | `ConfigManager`（Data 模式）**导出初值** + `Recorder` **运行时改写** | **禁止手改**（但运行时会被程序合法改写 —— 见 §2.4） |

### 2.2 为什么

- 每次执行 `ExcelTool/ExportExcelConfigs` / `ExportExcelModels` 都会**覆盖**这些文件
  （`FileUtil.SaveFile` 是 `Delete + WriteAllText`，**无备份**）。
- 实测（见 `02_配置表管线记录.md` §7）：导出会把产物 mtime 刷新为重写时刻。
- 手工加的字段/方法**必然丢失**，而且不会报错 —— 表现为"昨天还能编译，今天突然 CS 报错"。

### 2.3 需要给生成类加业务逻辑怎么办

**用 C# `partial`**（推荐，且这是说明文档 §12.5 给出的正规做法）：

```csharp
// 生成物不动。另建一个文件（不叫 ConfigData/*.cs，放业务目录）：
// Scripts/Runtime/MVP/Model/ConfigData/TestTableConfig.Runtime.cs   ← 手工文件，不进生成器
// 但生成器每次都重写 TestTableConfig.cs，所以：
//   ① 要么给生成器补 partial 关键字（需改 ConfigManager.cs → 交架构师排期）
//   ② 要么把业务逻辑放到外部扩展方法 / Service 类里，完全不碰生成类（当前最稳妥）
```

> ⚠ **当前生成器生成的类是 `public class {Name}{Mode}`，没有 `partial`**
> （`ConfigManager.cs:152`）。所以**现在做不到**"partial 拆分"。
> 在架构师排期之前，**业务逻辑必须放在生成类之外**（扩展方法、Service、Presenter）。

### 2.4 `Data/Records/*.record` 的特殊性

它**既是生成物又是运行时存档**：

- 导出器写初值（`ExportJson`，`ConfigManager.cs:221`）
- `Recorder.SaveData(save: true)` / `ForceSave()` 在运行时改写它（`Recorder.cs:115-135` / `:71-85`）

→ **不要把 `.record` 当作"必须保持与生成一致的产物"**。
它一旦被运行期改写，`git diff` 就会显示差异，这是**正常的**，不要"修正"它。
如果确实要恢复初值，**重新跑一次导出**，不要手写。

## 3. 【🟠】`.meta` 文件

### 3.1 规则

1. **每个资产/目录都必须有对应的 `.meta`，且 `.meta` 必须与资产一起提交。**
2. **不要手写、不要手改 `.meta`**（改 GUID 等于把所有引用打断）。
3. **不要删除 `.meta`** —— 删了 Unity 会生成一个新的 GUID，
   所有 Inspector 引用（预制体上的脚本、面板上的组件）**全部变成 `Missing (Mono Script)`**。
4. **`.meta` 的 GUID 冲突比缺失更糟**：两个资产共用一个 GUID 会导致其中之一被静默丢弃。
5. **移动/重命名资产要用 Unity 编辑器或 `AssetDatabase.MoveAsset`**，不要在文件系统里直接 `Move-Item` ——
   直接移动会留下孤立 `.meta`，Unity 重新生成 GUID，引用断掉。

### 3.2 现状提醒

`Story/` 下的 **`.md` 文件与子目录大多还没有 `.meta`**（例如 `Story/00_索引.md`、
`Story/01_企划/`、`Story/02_系统策划/`、`Story/04_架构/`、`Story/05_程序/` 都不存在对应的 `.meta`；
仅 `Story/README.md.meta`、`Story/03_配置表设计.meta`、`Story/03_配置表设计/01_配置表填写规范.md.meta` 等少数存在）。

这通常意味着 **Unity 还没导入这些新文件** —— Unity 会在下一次刷新时自动为它们生成 `.meta`。
**规矩：写完 Markdown 后切回 Unity 编辑器窗口触发一次刷新**，确认 `.meta` 生成后再一起提交；
否则别人拉下来会看到大量目录/文件差异，且 Unity 导入顺序不同会生成不同的 GUID。

### 3.3 自检（已把 `.git` / `.claude` 排除，否则会刷出上千条噪音）

```powershell
cd "D:\Unity Projects\Project_Chaos\Assets"
Get-ChildItem -Recurse -Force "Story","Scripts" -ErrorAction SilentlyContinue |
  Where-Object { $_.FullName -notmatch '\\\.git\\' -and $_.FullName -notmatch '\\\.claude\\' } |
  Where-Object { $_.Name -notlike "*.meta" -and -not (Test-Path ($_.FullName + ".meta")) } |
  ForEach-Object { $_.FullName.Replace("D:\Unity Projects\Project_Chaos\Assets\","") }
```

> ⚠ 上一版脚本漏了 `-notmatch '\\\.git\\'`，会把 `Excel\Chaos_excel\.git\**` 的上百个内部文件
> 全部列为"缺 `.meta`"。**`.git` 与 `.claude` 是工具目录，本来就不该有 `.meta`。**

### 3.4 ⚠ 仓库布局：`Assets/Story` 与 `Assets/Excel` **不在主仓库的版本控制内**

实测 `.gitignore`：

```
.gitignore:7:  Assets/Excel
.gitignore:8:  Assets/Story
```

**含义（交接时必须知道）**：

| 路径 | 归属 | 证据 |
| --- | --- | --- |
| `D:\Unity Projects\Project_Chaos\.git` | **主仓库**（Unity 工程） | `git rev-parse --show-toplevel` = `D:/Unity Projects/Project_Chaos` |
| `Assets/Story/**` | **被主仓库忽略** → 设计文档不进主仓库 | `git check-ignore -v` 命中 `.gitignore:8` |
| `Assets/Excel/Chaos_excel/.git` | **嵌套的独立仓库** → 配置表源表有自己的版本史 | `Get-ChildItem -Recurse -Directory -Filter .git` |

**推论与规矩**：

1. **`Story/` 下的文档改动不会出现在 `git status` 里**，也就**不会被主仓库提交**。
   → 不要用"`git status` 干净"来判断"文档没丢"。
   → 交接/备份 `Story/` 需要**单独的方式**（独立仓库、网盘、或让 Lead 决策）。
2. **`Assets/Story` 被忽略也意味着：Unity 不会为它生成 `.meta` 被提交**（§3.2 的现象由此而来），
   这在功能上无害（Markdown 不需要 GUID），但会让"缺 `.meta`"检查长期有噪音。
   → §3.3 的检查脚本应把 `Story` 当作**已知豁免区**看待。
3. **改 Excel 前先确认它在哪个仓库**：`Excel/Chaos_excel/` 是**另一个 git 仓库**，
   在主仓库里 `git add Assets/Excel/...` 是无效的（被 ignore）。
   → 配置表的版本管理走它自己的仓库，**这点必须转达策划**。
4. 我的三份交付物（`01`/`02`/`03`）已落在磁盘上，路径与内容均可正常读取；
   **但按上述 `.gitignore`，它们不会被主仓库跟踪** —— 这是工程既有约定，非本任务的疏漏。

> 另外：**`Excel/Chaos_excel/` 下嵌套了一个独立 git 仓库（`Excel/Chaos_excel/.git/`）**，
> 这是策划同步表格用的（含 `ugit` 工具痕迹）。→ 改 Excel 前先确认它属于哪个仓库，
> **不要在主仓库里误提交它内部的文件**。

## 4. 【🟠】命名空间

### 4.1 现状（不统一，改码时必须知道）

- `Scripts/Runtime/GameBase/` 下**绝大多数类在全局命名空间**（没有 `namespace`）：
  `EventManager`、`ResManager`、`UIManager`（真）、`BasePanel`（真）、`InputManager`、
  `ConfigManager`、`Recorder`、`GlobalPath`、`SettingsManager`…… 完整列表见
  `01_框架能力清单.md` §1.1。
- `ChaosDebug`：日志全家。
- `LocalizationSystem`：本地化全家。
- `TangLaoShi`：**废弃**。

### 4.2 规则

1. **不要给既有全局命名空间的类擅自加 `namespace`** —— 全项目没有任何 `using`，
   加 namespace 会一次性打断几十处引用。
2. **新增代码优先放进既有命名空间**（日志用 `ChaosDebug`、本地化用 `LocalizationSystem`）。
3. **新模块若要新建命名空间**，必须同时满足：
   - 不与既有全局命名空间里的类型重名；
   - 在 `01_框架能力清单.md` §1.1 的表里登记。
4. **永远不要 `using TangLaoShi;`**（见 §5）。
5. ⚠ **`OtherUIManager/` 下的 `UIManager` 与 `BasePanel` 与"真的"同名**。
   如果某个文件同时 `using TangLaoShi;` 且引用 `UIManager`，会拿到废弃那个，
   **只出 `[Obsolete]` 警告、不回错误**，然后运行时静默失效。
   排查手段：`grep -rn "using TangLaoShi" Scripts/` 应返回 0 条。

## 5. 【🟠】误引 `UnityEditor` 的构建风险

### 5.1 事实

`Scripts/` 下**没有任何 `.asmdef`**（实测），因此：

| 目录 | 编译进 | Player 构建时是否引用 `UnityEditor` |
| --- | --- | --- |
| `Scripts/Runtime/**` | `Assembly-CSharp` | ❌ **不引用** |
| `Scripts/Editor/**`（目录名恰为 Unity 特殊目录 `Editor`） | `Assembly-CSharp-Editor` | ✅ 引用（且不打包） |

→ **`Scripts/Runtime/` 里任何不在 `#if UNITY_EDITOR` 里的 `UnityEditor` 用法 = Player 构建失败。**

### 5.2 当前唯一的真实污染点（实测全量扫描）

| 文件 | 行 | 内容 | 受保护？ |
| --- | --- | --- | --- |
| `Scripts/Runtime/GameBase/ConfigManager/Config/ConfigManager.cs` | **9** | `using UnityEditor;` | ❌ **没有**（该文件 `#if UNITY_EDITOR` 从第 60 行才开始） |
| `Scripts/Runtime/GameBase/LogManager/LogBootstrap.cs` | 34 | `[UnityEditor.InitializeOnLoadMethod]` | ✅ 有（第 28 / 39 行） |
| `AudioManager.cs:34`、`ChaosLog.cs:166/194` | — | 仅注释/字符串 | 不构成引用 |

**本条本阶段只记录，不修**（交架构师在 `Story/04_架构/` 排期）。
两种修法：① 把 `using UnityEditor;` 移进 `#if UNITY_EDITOR`；
② 把 `ConfigManager` + `FileUtil` 整体挪到 `Scripts/Editor/`。

### 5.3 规则

## 6. 【🟠】编译门禁：每次改完 `.cs` 必须确认 0 error

### 6.1 规则

**改完 `.cs` 后不能只看"文件保存了"，必须让 Unity 重新编译并确认 0 error。**
Unity 编辑器在线（2022.3.57f1c2，MCP 端口 7890）。

### 6.2 怎么做

```
1) 让 Unity 刷新并编译（切回编辑器窗口 / 调 unity_execute_code 之类会触发刷新）
2) unity_get_compilation_errors(severity="all")   → 必须 count=0
3) unity_editor_state                              → isCompiling 必须为 false
4) unity_console_log(type="error", count=30)        → 不能有新的 error
```

### 6.3 注意

- **`unity_get_compilation_errors` 优先于 `unity_console_log`** ——
  它走 `CompilationPipeline`，**不受 Console 缓冲区被清空 / 被刷屏影响**。
- **`unity_console_log` 是快照，可能滞后**。本次实测就遇到过：
  导出产物的 mtime 已是 `15:15:34`，而 Console 快照最后一条停在 `15:15:29`
  （见 `02_配置表管线记录.md` §7.5）。→ **不要用"Console 里没看到日志"来推断"操作没执行"**，
  要用**副作用**（文件 mtime / 哈希 / `git status`）来判断。
- **判断"操作是否真的改了磁盘"用 mtime + SHA256，不要靠日志。**

## 7. 【🟡】Unity 操作必须走 MCP 工具

### 7.1 规则

- **所有 Unity 操作一律用 `unity_*` MCP 工具**（`unity_execute_code`、`unity_get_compilation_errors`、
  `unity_execute_menu_item`、`unity_scene_hierarchy` 等）。
- **严禁直接 HTTP 访问 `http://127.0.0.1:7890/api/...`** ——
  那会绕过多智能体队列、智能体归属追踪与安全机制。
- **多实例时每次调用带 `port`**。本工程当前只有 1 个实例（port 7890，Project_Chaos）。
- **改场景要谨慎**：非必要不要在 Edit Mode 里 `new GameObject()` / `Instantiate` / `SetActive` ——
  会把活动场景标记为 dirty，可能被误保存。
  - 本次任务实测：`MonoManager` 会在构造时 `new GameObject("MonoController")`（见 `01_框架能力清单.md` §4），
    所以**在 Edit Mode 里碰 `ResManager.LoadAsync` / `AudioManager` / `InputManager` 要自觉**。
  - 结束前用 `unity_scene_info` 确认 `isDirty == false`。

### 7.2 在 Edit Mode 里跑 `unity_execute_code` 的两个真实坑

**坑 1：`MonoManager` 的"僵尸缓存"**

`MonoManager` 是 `SingletonBase`（静态字段），但缓存了一个 `MonoController` 组件
（挂在它构造时创建的 GameObject 上）。该对象只有 `MonoController.Start()` 执行后才
`DontDestroyOnLoad`，而 **`Start()` 只在 Play Mode 跑**。

→ Edit Mode 里它的 GameObject 可能被清理，而静态缓存不会重置。
之后所有走 `MonoManager` 的调用（`ResManager.LoadAsync`、`AudioManager` 的构造、
`InputManager`、`ScenesLoadManager.LoadSceneAsync`）都会抛：

```
MissingReferenceException: The object of type 'MonoController' has been destroyed but you are still trying to access it.
```

**本次实测复现过 1 次。** → Edit Mode 的自动化/工具里**不要用异步加载**，改用同步 `Resources.Load`。

**坑 2：`SingletonMono` 在 Edit Mode 里 `GetInstance()` 返回 null**

`Awake` 在 Edit Mode 不执行，所以即使组件就在场景里，`GetInstance()` 也是 null。

**实测**：`LocalizationManager.GetInstance()` 返回 null，但 `Resources.FindObjectsOfTypeAll<LocalizationManager>()`
显示场景里**确实有 1 个实例**。→ **不要用 `GetInstance() == null` 判断"组件没挂"**，
要用 `FindObjectsOfTypeAll` 或看 `unity_scene_hierarchy`。
