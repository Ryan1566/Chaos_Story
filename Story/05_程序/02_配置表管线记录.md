### 3.2 ★重点：第 7 行到底会不会被导出 —— 文档与代码矛盾，实测站代码

**文档的说法**（`Excel配置表工具使用说明.docx`，第 3 章正文）：

> 「注意：导出时实际读取的是第 8 行及以后的数据。第 7 行虽然常量名写作"值行"，
> 但代码里取值循环从 `valueIndex + 1` 开始，因此第 7 行不会被导出——它相当于一行填写示例。」

**代码的实际写法**（`ConfigManager.cs:294-302`，注意是 `valueIndex` **而不是** `valueIndex + 1`）：

```csharp
private static string[] GetValues(ExcelWorksheet workSheet,int col)
{
    string[] values = new string[workSheet.Dimension.End.Row - valueIndex + 1];
    for(int row = valueIndex;row <= workSheet.Dimension.End.Row; row++)   // ← 从 7 开始，不是 8
    {
        values[row - valueIndex] = workSheet.Cells[row,col].Text;
    }
    return values;
}
```

**实测裁决**：导出的 `TestTableConfig.json` 有 **4** 条数据（张三/李四/王五/赵六），
其中"张三"就是 `ROW7`。并且 `GetValues` 的数组长度算的是
`End.Row - valueIndex + 1 = 10 - 7 + 1 = 4` —— 与"4 条"完全吻合。

```
[ResManager.Load] correct path len=563 datas=4 first=张三
```

> **结论：代码是从第 7 行开始取值的，第 7 行会被导出；文档第 3 章关于"循环从 `valueIndex + 1` 开始"
> 的陈述与代码不符，与实测结果也不符。文档描述错误，代码行为才是事实。**

### 3.3 类型白名单：**以 `ConfigManager.Convert` 为唯一权威**（T7 整改后终版）

> **权威来源**：`Story/README.md` §7。用户裁决（2026-10-05）：**配置表的 Type 上限以 `Convert` 支持的类型为准**。
> 本文档、`Assets/Learn/Excel配置表工具使用说明.docx`、任何表头模板**都不是权威**。
>
> **T7 已完成整改**（`Branch_feature_1`，主仓 `ConfigManager.cs`），本节已按整改后事实更新。

**新增一个类型必须同时过两道关**（缺一不可）：

1. 是**合法的 C# 类型名** —— `ExportClass`（`ConfigManager.cs:163-166`）把第 6 行文本**原样**当字段类型
   拼成 `public {类型} {字段};`；
2. 能被 **`UnityEngine.JsonUtility` 正确往返** —— 运行时读取链用的是 `JsonUtility.FromJson`。

#### 终版白名单：**12 个**

```
int   uint   long   ulong   byte   sbyte   short   ushort   float   double   bool   string
```

| 第 6 行填 | `Convert` | 生成的 C# 字段 | 结论 |
| --- | --- | --- | --- |
| `int` `uint` `long` `ulong` | ✅ | 同名字段 | 可用（原有） |
| `byte` `sbyte` `short` `ushort` | ✅ | 同名字段 | **T7 新增**，经端到端实测（**夹具未保留**，规格见下方"端到端验证证据"） |
| `float` `double` | ✅ | 同名字段 | 可用（原有） |
| `string` | ✅ | `string`，值**自动加双引号** | 可用（原有） |
| `bool` | ✅ | `bool`，值归一化为**裸** `true` / `false` | **T7 新增**；见下方取值规范 |
| **`int32` `int64` `long long`** | ❌ **直接拒绝** | — | **T7 已从 `Convert` 删除** |
| `decimal` | ❌ 拒绝 | — | **实测后否决，禁止加入** |
| `char` | ❌ 拒绝 | — | **实测后否决，禁止加入** |
| `enum` `DateTime` 等其它 | ❌ 拒绝 | — | 抛 `Exception("不支持此类型: xxx")` |

> **✅ T7 前 vs 后的关键变化**：整改**前**，`int32` / `int64` / `long long` 被 `Convert` **接受**并原样照抄，
> 结果生成**编译不过**的 C# 类（`public int32 Index;` → CS0246）——
> 症状是"一堆莫名其妙的编译错误"，而不是一条清楚的异常，排查成本高得多。
> **整改后这三个直接落到 `default` 分支，在【导出阶段】就抛「不支持此类型」**，
> 属于**期望的早失败**。所以旧文档里"会导出失败"的说法现在**成立**了
> （旧文档与旧代码当时确实矛盾，现已统一到"直接拒绝"）。

#### `bool` 的取值规范（归一化 + 早失败）

| 表里填 | 产出 JSON | 说明 |
| --- | --- | --- |
| `true` / `false`（不区分大小写，如 `TRUE`/`True`） | 裸 `true` / `false` | ✅ |
| `1` / `0` | 裸 `true` / `false` | ✅ **必需**，见下方实测 |
| `是` / `否` | 裸 `true` / `false` | ✅ |
| 空串 / 纯空格 / `随便` / `yes` / `2` 等 | — | ❌ **显式抛异常**，整批导出中断 |

> **为什么 `bool` 必须归一化成「恰好小写的裸值」**
> （Lead 2026-10-05 实测。⚠ 此前"JsonUtility 对 bool **大小写不敏感**、`"TRUE"` 也能解析"的说法**是错的** ——
> 那只对**带引号**形式成立；导出器产出的是**裸值**，所以大写会在运行期**直接抛异常**。）
>
> | 产出的 JSON | `JsonUtility.FromJson` 结果 |
> | --- | --- |
> | `{"b":true}` / `{"b":false}` | ✅ 解析成功 |
> | **`{"b":TRUE}` / `{"b":True}`** | ❌ **抛 `ArgumentException: JSON parse error: Invalid value.`** |
> | `{"b":"true"}` / `{"b":"TRUE"}` | ✅ 解析成功（**仅带引号形式**才大小写不敏感） |
> | `{"b":1}` / `{"b":0}` | ✅ 解析成功（数字） |
> | `{"b":是}` | ❌ 抛异常（语法上就不是合法 JSON） |
> | `{"b":"是"}` | ⚠️ **不报错，但静默解析成 `false`** —— 无声错值，最危险 |
>
> → **归一化成恰好小写的裸 `true` / `false` 是硬需求，不是"可选规范化"。**（下文"硬需求"三字即指此）
>
> 因此统一归一化成**规范的裸值** `true` / `false`（**不加引号**，绝不能与 `string` 归到一组）。
> 取值刻意**只留这 3 组同义词**（不再接受 `yes`/`y`/`no`/`n`）：多一套同义词就多一种填错方式。
>
> **⚠ 实测发现：`1` / `0` 别名是必需的，不是可选的。**
> 真实 xlsx 里若把单元格设成 **Excel 原生布尔**，EPPlus 的 `.Text` 取出来是 **`"1"`**（**不是 `"TRUE"`**），
> 所以不接受 `1`/`0` 就会把合法的原生布尔列判成非法。

#### 为什么 `decimal` / `char` 被否决（**实测后否决，禁止重新加入**）

| 类型 | 实测结果 | 结论 |
| --- | --- | --- |
| **`decimal`** | JsonUtility **静默丢弃**该字段：`ToJson` 输出里**根本没有它**，往返后**恒为 0** | ❌ **严禁加入** —— 这是"无声错值"，比抛异常危险得多 |
| **`char`** | 能往返，但 JSON 里存成**数字**（`'A'` → `65`） | ❌ 不纳入 —— 语义极易被误读 |

> 这两条已写进 `ConfigManager.Convert` 的 XML 注释（标注"实测后否决，禁止重新加入"），
> 防止后人凭直觉重新加回来。

```csharp
    //                                                                    ↑ 拼出 "Json/Runtime/TestTableConfig"

    //                                                                          ↑ 对 null 取 .text → NRE
    ChaosLog.Info(LogChannel.Config, "文件已同步解析完毕：" + typeof(T).Name);

```

**两个放大问题的设计**（修 bug 时值得一并考虑）：

1. `ResManager.Load` **找不到资源时静默返回 null**，连一条 warn 都没有（只有 `LoadAsync` 有 warn）。
   → 排查时只能看到一个 NRE，看不出是"路径拼错了"。
2. **`LoadData<T>` 里没有 try/catch**，异常直接抛给调用方。
   异步版本 `LoadDataAsync<T>` 反而有 `if (file != null && file is TextAsset ...)` 判空
   （`ConfigLoader.cs:34`）→ **只有同步版会炸**，异步版只会"静默返回 null"。

   实测异步版行为（本次因 `MonoManager` 的 Edit Mode 缓存问题未能取到干净结果，
   但从代码可确定它不会 NRE，而是走 `else` 分支打一条 WARN 并 `OnLoadCompleted(null)`）：

   ```

   OnLoadCompleted(result);   // result == null
   ```
   → **异步版的调用方必须判空**（`LoadConfigTest.cs:16-19` 就没有判空，直接 `json.datas[0]` → NRE）。

## 6. `ConfigLoader` / `Recorder` 是否重复实现同一件事？

Lead 提到的这个怀疑，核查结论如下（两者目标不同，**不是重复**，但有可统一的点）：

| 维度 | `ConfigLoader` | `Recorder` |
| --- | --- | --- |
| 文件 | `ConfigManager/Config/ConfigLoader.cs` | `ConfigManager/SL/Recorder.cs` |
| 读什么 | **Config 模式** 产物：`{T}Config.json` | **Data 模式** 产物：`{T}Data.record` |
| 从哪读 | `Resources.Load`（`ResManager`）→ **打包后只读** | `File.ReadAllText`（`Application.dataPath`）→ **打包后只读** |
| 实际读路径 | `GlobalPath.data_JsonPathToRead` ❌ **错位** | `Recorder.RecordPath` → `data_RecordPath` ✅ **正确** |
| 是否可写 | ❌ 只读 | ✅ 可写（`SaveData` / `ForceSave`） |
| 生命周期 | 无状态、无构造 IO | **构造函数就读全量磁盘**（`:55-65`） |
| API | `LoadData<T>()` / `LoadDataAsync<T>(cb)` | `LoadData<T>` / `SaveData<T>` / `CreateData<T>` / `UpdateData<T>` / `ReadData<T>` / `DeleteData<T>`×2 / `ForceSave` |
| `DataList<T>` | 声明在 `ConfigLoader.cs:53` | **共用**同一份 `DataList<T>`（在 `ConfigLoader.cs` 里） |
| 实测 | ❌ 抛 NRE | ✅ `datas=4 first=张三` |

> **两者职责不同（配置只读 vs 存档读写），不算重复实现。** 但存在三个"看起来重复"的地方需要留意：
>
> 1. **`DataList<T>` 定义在 `ConfigLoader.cs` 里**，却被 `Recorder` 复用 ——
>    若哪天删掉 `ConfigLoader`，`Recorder` 会一起编译不过。
> 2. **`FormatJson` 在 `ConfigManager.cs:424` 与 `Recorder.cs:232` 各有一份**（近乎逐行相同）——
>    这是真正的重复代码。
> 3. **`IModel` 声明在 `Recorder.cs:12`**，但 `Recorder` 自己**没有**实现它，
>    全项目**0 个实现**（实测 `[IModel] implementers=0 -> (none)`）。
>    说明文档 §12.2 说"唯一实现 `TestTableModel` 里 `throw new NotImplementedException()`"
>    —— **该文件已不存在**，这一条文档已过期。
> 4. **`Recorder.RecordPath` 用 `Application.dataPath`**，而 `SettingsManager` 特意改用
>    `persistentDataPath`（`SettingsManager.cs:22-24` 有说明）。→ **两套持久化，打包后
>    `Recorder` 的 `dataPath` 是只读的**，这是"游戏进度存档"必须提前解决的问题（见 §9 待决策项 5）。
