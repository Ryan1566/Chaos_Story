## 1. 系统概述

| 项目 | 内容 |
| --- | --- |
| 系统名 | 局内地图生成（RunMap Generation） |
| 所属模块 | `Story/01_企划/01_游戏概念案.md` 第 6 节 **M8 局内战斗 / 边缘空间**（主）＋ **M14 边缘空间的地形与各文明队伍**（地形部分） |
| 优先级 | MVP |
| 一句话说明 | 每局进入一个场景时，用「手作房间块 + 原型图」的混合方式生成一张含**地表 / 地下 / 地表建筑**三类空间层、且**保证连通与可通关**的横板地图，并把房间内可放敌人 / 掉落 / 事件的位置标记（`SpawnSlot`）交给战斗与养成系统填充 |
| 上游依赖 | M7 传送与派遣（本局种子、派遣人数）、M13 时代/难度（基础难度档）、M13b 深度（叠加增量）、M14 地形与阵营（主题） |
| 下游影响 | M8 局内战斗（战斗房与 boss 门）、M9 局内养成（掉落 / 事件位）、M10 扎营（扎营点房间）、M12 反哺带出（宝箱位）、M4 剧情事件（场景事件挂点） |
| 本系统涉及的配置表 | `MapBiome` / `MapPreset` / `PresetLayer` / `MapChunk` / `ChunkSocket` / `ChunkSlot`（草案见 §8） |

### 1.1 设计目标

| # | 目标 | 如何验证 |
| --- | --- | --- |
| G1 | **每局不同，但结构可预期**：玩家不会两次看到同一张图，也不会遇到"结构崩坏"的图 | 同一场景连续生成 10 次：房间总数与主路长度落在 §5 区间内的比例 = **100%**，且 10 次的房间块组合序列两两不同 |
| G2 | **一定连通、一定可通关**：不存在打不通的图 | 1000 组种子 × 每个主题：入口→boss 门存在通路 = **100%**，孤立房间数 = **0**（§13 A2/A3） |
| G3 | **三层空间可被玩家感知**：地表、地下、地表建筑都要出现 | 一局 3 个场景合计：地下 / 地表 / 地表建筑各至少出现 **1 次**（§13 A6）；层切换有明确提示（§9 U2） |
| G4 | **地图能承载玩法密度**：房间数量与大小够放战斗、事件、扎营 | 每场景战斗类房间数满足 M8 的敌人投放预算（`MapBiome.enemyBudget`），同屏敌人 ≤ **20**（对齐概念案 §9） |
| G5 | **生成不打断节奏**：玩家看不到"卡一下" | 生成在进入场景前完成：P95 ≤ **200 ms/场景**，单帧预算 ≤ **5 ms**（§13 A7） |
| G6 | **失败也有兜底**：任何异常都不产生无法通关的地图 | 注入"某类型房间块池为空"后仍能生成可通关的降级图（§13 A8）；降级路径见 §10 |

### 1.2 明确不做的（Non-goals）

| # | 不做的事 | 原因 |
| --- | --- | --- |
| N1 | **纯算法生成房间内部**（BSP / 元胞自动机 / 迷宫算法直接生成地形） | 横板动作对"平台布局与手感"的要求远高于拓扑正确性；**策划建议**：算法只用于房间块内部的**装饰变体**，不作为主生成手段（§3.4） |
| N2 | **Dead Cells 式的"多出口选路"**（同一关有 2~3 个出口通向不同下一关） | 本作是**一局 3 个场景固定顺序**推进（概念案 §5.2），不存在分支选路；`策划建议`：场景内的**支路**仍保留（走不走支路由玩家决定），但不改变场景顺序 |
| N3 | **可变尺寸房间块**（同一张图里混用 1 屏 / 2 屏 / 半屏块） | 拼接与回溯复杂度成倍上升；MVP 只做**统一尺寸 + 3 档出口高度**（§4.3），字段预留（`sizeClass`）不实现 |
| N4 | **单向门 / 永久封路**（跳下不可回、塌方封路） | 与"局内不限时、可慢慢探索"的基调冲突，且容易制造卡死；MVP 只做双向通道（`socketType=4` 预留不启用） |
| N5 | **联网 / 多人同步地图**（种子下发、服务端校验） | 概念案 N1：纯单机，不引入任何需要服务端校验的逻辑 |
| N6 | **3D / 非横板视角** | 概念案 §3/§9：2D 横板、卷轴跟随 |
| N7 | **运行时动态改图**（战斗中途开墙、随机事件改地形） | MVP 不做；地图在进入场景前一次性生成完成，之后只读 |

## 2. 术语表

> 术语命名一律「待定稿」；最终以用户确认（§14 Q9）与 `Story/01_企划/01_游戏概念案.md` §11 的术语表为准。

| 术语 | 含义 | 代码 / 配置表命名建议 |
| --- | --- | --- |
| **空间层** | 地图的纵剖分层：1 地下 / 2 地表 / 3 地表建筑（4 屋顶，预留） | `MapLayer`（**待定稿**） |
| **深度** | 概念案 §5.3 的**难度轴**（跨局累积、上限 = 时代序号） | `Depth`（**与空间层无关**） |
| **房间块** | 手工制作的预制关卡单元，可拼接、带接口与标记点 | `Chunk` / `RoomChunk`（**待定稿**） |
| **接口** | 房间块边界上的可通行口，有方向与高度档 | `Socket`（**待定稿**） |
| **原型图** | 每张地图的抽象骨架（层顺序、主路长度、支路数、特殊房数量） | `MapPreset`（**待定稿**） |
| **主路** | 从入口房间到 boss 门的必经链路 | `MainPath`（**待定稿**） |
| **支路** | 从主路分叉、最终回接主图或通向奖励房的侧链 | `Branch`（**待定稿**） |
| **跨层连接件** | 同时属于上下两个空间层的连接房间块（楼梯间 / 竖井 / 塌方口 / 升降机） | `LayerLink`（**待定稿**） |
| **房间格** | 网格布局的最小单位；MVP 中 1 个房间格 = 1 个房间块 | `Cell`（**待定稿**） |
| **标记点** | 房间块内预留给敌人 / 宝箱 / 事件 / 装饰的位置 | `SpawnSlot`（**待定稿**） |
| **局种子 / 场景种子** | 一局的随机种子 / 由它派生的单场景种子 | `RunSeed` / `SceneSeed`（**待定稿**） |
| **图版本** | 地图生成规则与房间块库的版本号，用于读档兼容判断 | `mapVersion`（**待定稿**） |
| **保底布局** | 生成连续失败的最终降级形态（链式主路 + 通用块） | `FallbackLayout`（**待定稿**） |

> ⚠️ **必须分清的三个"层"**（本作容易混）：
> ① **空间层 `MapLayer`** = 地图纵剖（地下 / 地表 / 地表建筑）—— 本系统管的；
> ② **深度 `Depth`** = 跨局累积的难度轴，上限 = 时代序号 —— 概念案 §5.3 管的，**不是空间层**；
> ③ **场景序号**（1/2/3）= 一局内的推进顺序 —— M8 管的。
> 三者互不等价，写文案与做 UI 时**不得混用"层数"这个词**（概念案 §10 R11 已就类似可读性风险提过醒）。

## 3. 参考分析：死亡细胞（Dead Cells）的地图生成技术

> ⚠️ **资料来源说明**：本节基于**公开的二手复盘资料**（原文作者为 Dead Cells 的关卡设计 Sébastien Bénard，本策划读到的是中文编译与本项目外部文档），
> **仅用于选型论证**，不作为权威事实；引用见 §15。凡本节中无来源支撑的推断，标注「策划推断」。

### 3.1 Dead Cells 的做法：**混合式生成（Hybrid approach）**，共六步

| 步 | 做法 | 关键点（对本项目的启示） |
| --- | --- | --- |
| ① **先定死不变的元素** | 关卡的整体设计风格、不同地点如何衔接、新通路如何开启等**不随随机改变**的基本要素，全部事先设计 | 随机只发生在"设计留出的空位"上；**框架不变、内容变** |
| ② **手作一大批预制地图块（Tile / Chunk）** | 每块都有不同的表现与**可配置参数**；块有**主题属性**（"监狱"的块绝不会出现在"下水道"关卡里） | 块的多样性 = 可玩性；**主题约束**防止风格穿帮 |
| ③ **每张大关一张原型图（概念图）** | 用节点图管理预制块：从出入口开始，再放特殊房间（宝藏、商店），最后是战斗与探索段落。原型图产出**可调参数**：关卡长度、特殊块数量、迷宫复杂度、入口到最近出口之间有多少块 | **先有骨架、后有块**；策划能对"宏观手感"调参（堡垒平铺直叙、下水道蜿蜒曲折） |
| ④ **逐节点选块 + 校验** | 对每个节点随机取一个符合主题的块，**检查它是否满足设计要求（出口的位置、数量、类型）**，不符合就换下一块再试 | **出口（接口）是拼接的唯一契约**；"随机 + 校验 + 重试"是可实现的判据 |
| ⑤ **按原型图投放敌人** | 原型图定义了多少个战斗块，就按"每 N 个战斗块一个敌人"投放；单个敌人有自己的限制：稀有度、是否唯一、能否与其它敌人同平台、需要多大空间 | **敌人密度由地图参数反推**，不在关卡里手摆 |
| ⑥ **生成掉落与宝物** | 官方未公开细节（原文"卖了个关子"） | 掉落规则独立于地图结构，**由本作 M9/M12 自己定**（本文只出位置标记） |

补充要点（同一资料）：

- Dead Cells 团队认为纯手工做不完、纯随机会"不精妙、不连贯"，**混合方案**是被验证过的正解。
- 他们也做了类似 L4D「AI Director」的节奏调节（动态调敌人生成与节奏）——**本作 MVP 不做**，登记为后续可选（§14 Q4 之外的延伸）。
- Spelunky 的对照案例：**4×4 网格 + 先随机出一条"关键路径（critical path）"，再补齐非路径房间，最后按"必含出口方向"给每个格子选房间模板（类型 0/1/2/3）**；同一模板靠每格瓦片的随机属性产生"看起来完全不一样"的效果。

### 3.2 把这些做法抽象成三条可复用的原则

| # | 原则 | 说明 |
| --- | --- | --- |
| P1 | **拓扑先于几何** | 先生成"房间图"（谁连着谁），再把图嵌入网格坐标（在哪一格），最后才选具体块与实例化。**顺序颠倒会导致大量回溯** |
| P2 | **接口即契约** | 两块能不能拼，只看"方向 + 高度档"是否匹配；把接口规格**收敛成有限几档**（本作 3 档），比"任意高度都能接"更可控 |
| P3 | **生成必须可判定** | 每一步都要有机器可校验的判据（连通性、房间数区间、接口匹配、boss 唯一），校验不过就重试，重试用尽就降级 |

### 3.3 与本项目的差异（不能照搬的地方）

| 项 | Dead Cells | 本项目（Project_Chaos） |
| --- | --- | --- |
| 局内结构 | 一张大关 → 多出口 → 玩家选路线（分支 biome 网） | **一局固定 3 个场景，顺序不可选**，每场景末尾 boss（概念案 §5.2 / §14.3） |
| 空间形态 | 单层横向卷轴为主（有少量上下错层） | **明确要求地表 / 地下 / 地表建筑三类空间层**（用户本次需求） |
| 时间压力 | 有节奏调节（AI Director 风格） | **局内完全不限时（含 boss 战）**（概念案 §14.3 Q2）→ 生成不需要"节奏调速"，但**更需要"不迷路、不卡死"** |
| 团队产能 | 专职关卡设计团队 + 大量美术块 | 小团队：MVP 用**灰盒占位块**先验证管线（§14 Q6） |
| 工程约束 | 自研引擎 / CastleDB 配置 | Unity 2022.3 + **Excel 导出器 12 类型白名单、无 enum、不支持嵌套结构**（`Story/README.md` §7）→ 表必须**拆表 + 外键** |

### 3.4 结论：本项目的选型

| 选项 | 结论 |
| --- | --- |
| 纯手工逐关设计 | **否决**：与"每局不同"的肉鸽前提冲突，工量不可接受 |
| 纯算法生成（BSP / CA / 迷宫） | **否决（作为主手段）**：拓扑能生成，但"横板平台布局 + 战斗手感 + 美术一致性"不可控；**策划建议**只用作房间块内部的装饰变体 |
| **手作房间块 + 原型图 + 运行时按接口拼装（混合式）** | **采纳**：即 §3.1 六步的裁剪版，落地为 §6.2 的 **Pass A~F**；差异按 §3.3 处理 |

**映射关系（死亡细胞六步 → 本系统 Pass）**：

| Dead Cells | 本系统 | 产物 |
| --- | --- | --- |
| ① 固定元素 | `MapBiome` 表 + `MapPreset` 表（策划配置） | 主题、层结构、房间数区间、重试上限 |
| ② 预制块库 | 房间块 prefab + `MapChunk` / `ChunkSocket` / `ChunkSlot` 表 | 可拼接的块 + 接口 + 标记点 |
| ③ 原型图 | `MapPreset` + `PresetLayer`（层顺序与层间规则） | 抽象房间图（节点/边/层标签） |
| ④ 逐节点选块 + 校验 | Pass D `ChunkPicker` + §4.4 硬规则 | 每格实际使用的房间块 |
| ⑤ 敌人投放 | Pass F 输出 `SpawnSlot` 列表 → **交 M8 填充** | 本系统**不生成敌人**，只给位置 |
| ⑥ 掉落宝物 | 同上 → **交 M9 / M12 填充** | 本系统只给位置 |

## 4. 规则详述

> 每条规则都要能被测试用例覆盖。编号 `C` 为**硬规则**（不可配置，违反即生成失败），`S` 为**可配置规则**（表驱动）。

### 4.1 空间层模型（`MapLayer`）

| 值 | 名称 | 说明 |
| --- | --- | --- |
| 1 | 地下 | 洞穴、地道、地下水源等；无自然光 |
| 2 | 地表 | 地面、村庄外围、旷野、营地 |
| 3 | 地表建筑 | 建筑室内 / 建筑外立面平台（塔楼、城墙、屋架）；**必须经地表进入** |
| 4 | 屋顶 | **预留**，MVP 不实现（`layerMask` 位 8） |

**规则**：

| # | 类型 | 规则 | 触发条件 | 结果 | 例外 |
| --- | --- | --- | --- | --- | --- |
| S1 | 可配置 | 一张场景地图由 **1~3 个空间层**组成 | 生成开始时 | 层组合由 `PresetLayer` 的 `layerOrder` 序列决定 | 主题 `layerMask` 未包含的层不得出现 |
| C1 | 硬 | **一局 3 个场景合计，三层（1/2/3）各至少出现 1 次** | 一局开始时分配 3 个场景的 preset | 若自动分配结果不满足，则从候选 preset 中重新分配（最多 20 次）；仍不满足 → 强制场景 1 含地下、场景 3 含地表建筑 | 无 |
| S2 | 可配置 | 每场景层数 **2~3**（MVP） | 同上 | 少于 2 层的 preset 仅允许在 1 层主题内使用（MVP 无此类主题） | 后续可放宽为 1~3 |
| C2 | 硬 | **地表建筑层（3）只能与地表层（2）直接相连** | 层间规则校验时 | `layer=3` 的行，其 `linkFromLayerOrder` 必须指向一个 `layer=2` 的层；违反即 preset 非法（加载时报 error 并跳过该 preset） | 若将来引入"塔楼直通地下"，须先改本规则并登记 |

### 4.2 地图总体结构

```
      [入口房 (layer2)]  ← 玩家出生
             │
      [战斗房 (layer2)] ──── [宝藏房 (layer2)]        ← 支路（死路奖励）
             │
      [竖井   (layer1↔2)]  ← 跨层连接件（同时属于两层）
             │
      [战斗房 (layer1)] ──── [事件房 (layer1)]        ← 支路
             │
      [楼梯   (layer2↔3)]
             │
      [战斗房 (layer3)] ── [扎营点 (layer3)] ── [BOSS 门 (layer3)]  ← 叶子节点（入度 1 / 出度 0）
```

| # | 类型 | 规则 | 触发条件 | 结果 | 例外 |
| --- | --- | --- | --- | --- | --- |
| C3 | 硬 | **boss 门房间块唯一，且在图上是叶子**（入度 = 1、出度 = 0） | 每次生成结束 | 校验失败 → 本次生成作废重试 | 无 |
| C4 | 硬 | **入口房唯一**（`chunkType=1`），且入度 = 0 | 同上 | 同上 | 无 |
| C5 | 硬 | 主路房间数落在 `[mainPathMin, mainPathMax]` 内，床位（支路总数）落在 `[branchMin, branchMax]`，房间总数落在 `[totalMin, totalMax]` | 同上 | 越界 → 截支路 / 追加通用支路 / 重试 | 重试用尽走降级（§10 E6） |
| C6 | 硬 | 特殊房数量**恰好等于**配置值（宝藏 `specialTreasure` / 商店 `specialShop` / 事件 `specialEvent` / 扎营点 `specialCamp`） | 同上 | 少于配置 → 在满足接口的支路上补齐；多于配置 → 丢弃多余 | 块池不足时允许少于配置，记 warn（§10 E1） |

### 4.3 房间块与接口（Socket）规范

**房间块 prefab 结构（MVP 约定）**：

```
<ChunkRoot>                        ← 1 个房间里块 = 1 个布局格
 ├─ Grid
 │   ├─ Tilemap_Ground             ← 可行走地面 / 墙体（含 TilemapCollider2D + CompositeCollider2D）
 │   ├─ Tilemap_Deco               ← 纯装饰（无碰撞）
 │   └─ Tilemap_Foreground         ← 前景遮挡（可选）
 ├─ Socket_L / Socket_R / Socket_U / Socket_D   ← 出口空物体（位置 = 门/通道中心；命名固定）
 ├─ SpawnSlot_01 … SpawnSlot_NN    ← 标记点空物体（与 ChunkSlot 表一行一一对应）
 ├─ CameraBounds                   ← 房间相机边界（BoxCollider2D，仅用于取包围盒）
 └─ RoomMarker                     ← 房间根标记（供程序索引，挂房间 ID 与层号）
```

| # | 类型 | 规则 | 触发条件 | 结果 | 例外 |
| --- | --- | --- | --- | --- | --- |
| S3 | 可配置 | 块的**尺寸档** `sizeClass`：1 标准（1 格）；2 小（0.5 格，建筑室内）；3 大（2 格） | 选块时 | MVP **只允许 1**（其它值视为非法，加载时报 error） | 后续扩展，需先改 §7.1 布局算法 |
| C7 | 硬 | 块的**接口高度档**只有 3 档，且档位 = **出口地板行**（不是门洞中心）：`0 低` / `1 中` / `2 高`。标准块高 H = 24 格时为第 **3 / 11 / 18** 行（自底向上、0 起算，约占块高 12% / 46% / 75%），门洞 = 该行起往上 **4 格** | 拼接时 | 两块能拼 ⟺ 方向相反、`heightProfile` 相等，**且两侧地板行相同** | 块内可做斜坡/落差，但**接口地板**必须精确落在档位上；块高变更时全库同步重算（口径与实测见 §16） |
| C8 | 硬 | **块的最小可离开性**：除 boss 门（`chunkType=10`）外，每个块的 `socketMask` 至少要有 **2 个方向**，且至少 **1 个方向与"入口方向"不同** | 房间块入库时静态校验 | 不满足的块**不得进库**（§13 A9） | 死路奖励房（`chunkType=11`）允许只有 1 个接口，但必须是"进入方向的反向"可返回 |
| C9 | 硬 | 每个块的 `prefabPath` 必须真实存在，且 `socketMask` 与 prefab 内的 `Socket_*` 子物体**一一对应** | 加载与生成时 | 不一致 → 该块被跳过并记 error（§10 E11） | 无 |
| S4 | 可配置 | **主题约束**：块只能出现在自己的 `biomeId` 中（如"地下"的块不得出现在"地表建筑"主题里） | 选块时 | 从同主题块池中抽取 | 允许标记"通用块"（`biomeId=0`）跨主题复用（MVP 建议不做） |
| S5 | 可配置 | 块的**出现次数限制**：`isUnique=true` 全图 1 次；否则受 `maxCount` 限制 | 选块时 | 超限的块从候选池剔除 | 块池耗尽 → §10 E1 |

### 4.4 连通性硬规则（本次需求的重点）

| # | 硬规则 | 判定方法 | 失败处理 |
| --- | --- | --- | --- |
| **C10.1** | **全图连通**：从入口房出发可到达每一个房间 | 对房间图做 BFS，计数 = 房间总数 | 丢弃未达房间并重校验 → 仍失败：整图重生成（计入 `retryMax`） |
| **C10.2** | **入口 → boss 门必有主路**，且主路长度 ∈ `[mainPathMin, mainPathMax]` | 入口到 boss 门的最短路径长度（房间数） | 重生成；重试用尽 → 保底布局（§10） |
| **C10.3** | **接口匹配**：任意相邻两块的接口方向相反且 `heightProfile` 相等 | 遍历边逐条比对 | 该边作废 → 换块重选（换块上限 = `MapPreset.retryMax`） |
| **C10.4** | **每层内部连通**：同一 `layer` 的房间在其所属层内互相连通 | 按层分组后各自 BFS | 丢弃该层孤立房 → 重校验 |
| **C10.5** | **层间连接数 ∈ `[linkMin, linkMax]`**：每个"层对"（由 `PresetLayer.linkFromLayerOrder` 定义）之间至少有 1 个跨层连接件 | 统计连接件的边数 | 少于下限 → 在接口允许的位置补一个连接件；无法补 → 重生成 |
| **C10.6** | **跨层连接件上下接口网格坐标必须对齐**（同一列 `cellX`） | 布局阶段按 `cellX` 相等校验 | 布局阶段直接判为冲突并另择位置（§6.2 Pass C） |
| **C10.7** | **禁止地下层（1）直连地表建筑层（3）**（C2 的运行时体现） | 层间边校验 | 非法边作废 → 重选 |
| **C10.8** | **不产生死锁**：除 boss 门外，不存在"只有 1 个通口且该通口是入口方向"的房间（即玩家进去后无法离开） | 遍历所有房间的 `socketMask` 与被使用方向 | 该房间降级为死路奖励房或剔除，再校验 |
| **C10.9** | **boss 门是唯一的终点**：除 boss 门与死路奖励房外，每个房间至少有 1 条通向"可达区域"的路径 | 反向 BFS（从 boss 门回推） | 不满足的房间被标记为"未接入" → 同 C10.1 处理 |
| **C10.10** | **不产生封闭区域**：任何两个房间之间不存在"必须穿过 boss 门才能互通"的情形 | 在"去掉 boss 门"后的图上做连通性检查 | 重生成 |

> **生成后 100% 校验**：以上 10 条任一失败 → 按"局部修补 → 换块 → 整图重生成（≤ `retryMax`）→ 保底布局"的顺序处理，**绝不把校验不通过的地图交给玩家**。

### 4.5 规则之间的优先级

```
硬规则（C 系列，违反即失败）
  > 主题约束（S4）
    > 数量约束（C5 / C6 的目标值）
      > 表现偏好（层顺序、特殊房位置、权重抽取）
```

同一节点同时满足多条候选时：**先满足接口匹配（C10.3）→ 再满足数量约束 → 最后按 `weight` 抽取**。

### 5.1 取整与边界

| 项目 | 规定 |
| --- | --- |
| 取整方式 | 房间计数、权重、重试次数一律**向下取整**；比例计算（层占比、主路占比）**四舍五入到整数** |
| 最小值 | 房间总数下限 = 6（低于 6 的 preset 视为非法并记 error）；主路房间数下限 = 3；每个层对连接件下限 = 1 |
| 上限截断 | 超过 `roomMax` 的房间一律截断并回收；`retryMax` 用尽后不再重试，直接走保底布局 |
| 种子为 0 | `RunSeed = 0` 视为非法输入 → 用当前时间戳生成新种子并记 warn（**不得崩溃**） |
| 层数越界 | 主题 `layerMask` 不含的层，preset 中对应行直接被跳过（不报错，记 info） |

## 6. 状态与流程

### 6.1 生成状态机

| 状态 | 进入条件 | 允许的动作 | 退出条件 | 去向 |
| --- | --- | --- | --- | --- |
| `Idle` | 未进入局内地图 | 接受"生成请求" | 收到 `(RunSeed, era, depth, sceneIndex)` | `Setup` |
| `Setup` | 收到生成请求 | 读表、校验 preset 合法性、计算 `SceneSeed` | preset 合法 | `GraphGen` |
| `Setup` | 同上 | — | preset 非法 / 表缺失 | `Fallback`（记 error） |
| `GraphGen` | preset 合法 | Pass A~B：生成抽象房间图 | 图满足 C3~C6 | `Layout` |
| `GraphGen` | 同上 | — | 次数 > `retryMax` | `Fallback` |
| `Layout` | 图已生成 | Pass C：图嵌入网格（冲突回溯） | 全部节点落位无冲突 | `PickChunk` |
| `PickChunk` | 节点已落位 | Pass D：按接口选块 | 每格都有合法块 | `Instantiate` |
| `PickChunk` | 同上 | — | 换块次数超限 | `GraphGen`（退一步重生成） |
| `Instantiate` | 已选块 | Pass E：实例化 + 层间连接 + 相机边界 | 实例化完成 | `Populate` |
| `Populate` | 已实例化 | Pass F：输出 `SpawnSlot` 列表、写校验结果 | 校验 C10.1~C10.10 全过 | `Ready` |
| `Populate` | 同上 | — | 校验失败 | `GraphGen` / `Fallback` |
| `Fallback` | 重试耗尽 / 缺表 / 超时 | 生成保底布局（链式主路 + 通用块） | 保底图生成完成 | `Ready`（标记降级） |
| `Ready` | 校验通过或保底完成 | 广播 `MapReady`；接受"标记房间已清理" | 玩家到 boss 门并通过 | `SceneTransition` |
| `SceneTransition` | 场景通关 | `sceneIndex + 1` | `sceneIndex ≤ 3` | `Setup`（下一场景） |
| `SceneTransition` | 同上 | — | `sceneIndex > 3` | `Idle`（本局结束） |

### 6.2 生成流水线（Pass A~F，与死亡细胞六步的对应见 §3.4）

```
Pass A 参数装配   读 MapBiome / MapPreset / PresetLayer，算 SceneSeed，校验 preset
      ↓
Pass B 抽象图     生成 RoomNode / RoomEdge：入口 → 主路 → boss；按层顺序切片；插支路；放特殊房
      ↓（图先用"度"描述，不带坐标）
Pass C 网格布局   图嵌入 2D 网格：每节点占 1 格，按方向偏移放置，冲突则回溯换向
      ↓（带上 cellX / cellY / layer）
Pass D 选块       逐格按 (layer, chunkType, socketMask, heightProfile) 从块池抽取，
      ↓           校验接口匹配（C10.3）与出现次数限制（S5），不匹配换下一块
Pass E 实例化     按坐标实例化块 prefab；放置跨层连接件（要求 cellX 对齐，C10.6）；
      ↓           设置房间相机边界；把块挂到地图根节点下
Pass F 填充+校验  输出 SpawnSlot 列表交 M8/M9/M12；跑 C10.1~C10.10 全量校验；
                 失败 → 回到对应 Pass（换块 → 重生成 → 保底）
```

**各 Pass 的失败处理**：

| Pass | 失败情形 | 处理 |
| --- | --- | --- |
| A | preset 不存在 / `layerMask` 与 `layer` 冲突 | 用默认 preset（`presetId=1`）+ error 日志 |
| B | 图不满足 C3~C6 | 重生成（≤ `MapBiome.retryMax`） |
| C | 网格冲突（目标格被占） | 依次尝试其余方向 → 仍冲突则改支路走向 → 仍冲突则丢弃该支路节点 |
| D | 无匹配块 | 放宽 `minMainPathIndex` 限制 → 放宽 `weight` → 使用同 `chunkType` 的通用块 → 丢弃该节点 |
| E | prefab 缺失 / 资源加载失败 | 记 error，回到 D 重选（最多 3 次），仍失败 → 使用该 `chunkType` 的兜底块 |
| F | 校验失败 | 按 §4.4 的"失败处理"列逐条处理 |

### 6.3 时序（涉及多系统）

| 顺序 | 发起方 | 接收方 | 消息 / 调用 | 备注 |
| --- | --- | --- | --- | --- |
| 1 | M7 传送派遣（局外） | 本系统 | 生成请求 `(RunSeed, era, depth, sceneIndex)` | 种子在**局外**生成并保存 |
| 2 | 本系统 | 配置读取 | 按 `era` / `depth` / `biome` 取表行 | 见 §11 D1（读表通路当前有 P0 缺陷） |
| 3 | 本系统 | 自身 | Pass A~F | 可在读条界面内异步分帧执行 |
| 4 | 本系统 | 读条界面 | 进度事件（0 ~ 100%） | 复用 `EventConstName.LoadProgress` 或新增事件名（须登记） |
| 5 | 本系统 | M8 战斗 | `MapReady`：房间图 + 各房间坐标 + 出生点 + `SpawnSlot` 列表 | **本系统不生成敌人** |
| 6 | M8 / M10 | 本系统 | "房间已清理" / "已扎营" | 用于小地图与支路提示 |
| 7 | 本系统 | M9 / M12 | 宝箱位 / 掉落位就绪 | 由奖励系统决定具体内容 |
| 8 | M8 | 本系统 | 玩家通过 boss 门 | `sceneIndex + 1` → 回到 `Setup` |

> 事件名一律登记到 `Assets/Scripts/Runtime/GameBase/EventCenter/EventConstName.cs`，**禁止裸字符串事件名**（`chaos-arch-standard` §4）。

### 7.2 需要存档的数据

> 存档规则遵守 `Story/02_系统策划/00_系统设计文档模板.md` §6：**只能用 `public` 字段或带 `[SerializeField]` 的私有字段；只读属性会被静默丢弃。**

| 字段 | 类型 | 含义 | 需要存档？ | 版本兼容要求 |
| --- | --- | --- | --- | --- |
| `runSeed` | `uint` | 本局种子（布局可完整复现） | **是** | 必存 |
| `sceneIndex` | `byte` | 当前场景 1~3 | **是** | 必存 |
| `mapVersion` | `ushort` | 生成规则/块库版本 | **是** | 不匹配 → 重生成（§10 E8） |
| `clearedRoomIds` | 列表 | 已清理房间（用于小地图与"是否重打"判断） | **是** | 只存房间 ID 列表 |
| 房间布局 / 坐标 / 选块结果 | — | — | **否** | 由种子 + `mapVersion` 复现，**不入档**（避免存档膨胀与跨版本不一致） |

> ⚠️ 本系统**不新建存档表**；上表字段由 M15 存档系统统一承载（`Data` 模式的表由 M15 定义）。

### 7.3 图版本与兼容

| 场景 | 行为 |
| --- | --- |
| `mapVersion` 相同 | 用种子完整复现原布局 |
| `mapVersion` 不同（房间块库或生成规则改过） | **允许重生成**：用同一 `runSeed` 生成"新版本下的新图"，当前房间标记为已探索；**不报错、不崩档**；若玩家正在场景中，提示文案"地图布局已更新"（本地化 key 见 §9） |
| 房间块被删除导致 `chunkId` 失效 | 该房间标记为"未知块" → 用同 `chunkType` 的兜底块顶替 + 记 error |

## 10. 边界与异常

| # | 场景 | 期望行为 | 是否需要提示玩家 |
| --- | --- | --- | --- |
| E1 | 某 `(biome, layer, chunkType)` 的房间块池为空 | 记 `Error` → 放宽到同 `layer` 的通用块 → 仍无则用同 `chunkType` 的任意主题块 → 仍无则丢弃该节点并保主路 | 否 |
| E2 | `presetId` 在表中不存在 / `biomeId` 悬空 | 使用默认 preset（`presetId = 1`）+ `Error` 日志；若默认也不存在 → 直接走保底布局 | 否 |
| E3 | 接口无法匹配（找不到合适的下一块） | 回溯换块（≤ `MapPreset.retryMax`）→ 放宽 `minMainPathIndex` / `weight` → 丢弃该支路节点，保主路 | 否 |
| E4 | 网格冲突（目标房间格已被占用） | 依次尝试其余方向 → 改支路走向 → 丢弃该支路节点 | 否 |
| E5 | 生成后仍有孤立房间 | 回收孤立房间 → 重跑校验 → 仍失败则整图重生成（计入 `retryMax`） | 否 |
| E6 | 房间总数低于下限 / 高于上限 | 低于下限：追加"通路类"通用房；高于上限：截断支路并回收 | 否 |
| E7 | `RunSeed = 0` 或非法种子 | 用当前时间戳重算种子 + `Warn`；**不崩溃** | 否 |
| E8 | 读档时 `mapVersion` 不匹配 | 用同一 `runSeed` 重生成新图，当前房间标记为已探索 | 是（U7 轻提示） |
| E9 | 玩家卡进地形 / 掉出地图边界 | 检测到玩家 Y 低于地图下限或长时间无地面接触 → 传送回**本房间入口**（防卡死保底） | 否（可加一次屏幕闪白） |
| E10 | 单帧生成超过预算（5 ms）或总耗时超过 3 s | 分帧继续（读条界面保持）；超过 3 s 强制走保底布局 | 否（读条界面本身即提示） |
| E11 | 房间块 prefab 缺失 / `socketMask` 与 prefab 子物体不一致 | 记 `Error` → 该块跳过并重选（≤ 3 次）→ 使用同 `chunkType` 兜底块 | 否 |
| E12 | 配置表整体缺失 / 被删到 0 行 / 读表通路不可用（当前 P0） | 记 `Error` → 直接使用**内置的保底 preset 常量**（不依赖表）生成链式地图 → 保证能玩 | 否 |
| E13 | 玩家重复触发"进入场景"（连点 / 快速切场景） | 生成请求加互斥锁（生成中忽略新请求） | 否 |
| E14 | 支路全部被丢弃导致探索感过低 | 记 `Warn`（含被丢弃节点数与原因），供策划调参；玩家无感 | 否 |

### 12.3 关键实现约定（避免踩项目已知的坑）

1. **随机数**：使用**独立** RNG 实例（每次生成从 `sceneSeed` 起算），**禁止使用 `UnityEngine.Random` 的全局状态**（会与其他系统互相干扰，破坏可复现性）。
2. **确定性**：房间遍历、块池排序、字典遍历必须**显式排序**（不依赖哈希顺序），否则同一 seed 两次结果可能不同。
3. **生成时机**：在进入场景前（读条界面内）异步分帧生成；**不阻塞主线程超过 5 ms/帧**（F10）。
4. **脚本编码**：`Scripts/` 是混合编码（GBK / UTF-8+BOM / UTF-8），新增 `.cs` 用 UTF-8，改动既有文件必须保持原编码（skill `chaos-safe-csharp-edit`）。
5. **`Scripts/Runtime/` 禁止 `using UnityEditor`**；需要编辑器逻辑走 `#if UNITY_EDITOR` 或放 `Scripts/Editor/`。
6. **新路径常量必须进 `GlobalPath`**（如房间块资源前缀），不要散落字符串。
7. **命名**：不使用保留后缀 `Config` / `Data`（那是生成物专用）。
8. **不做**：不引入第三方程序化生成框架（Edgar 等）作为运行时依赖；若要参考，只借鉴算法思路（工程当前无相关包，新增依赖需评估）。

## 16. 美术资产与占位（灰盒）资产规格

> **本节记录已落地的"程序化灰盒"资产管线**（用户 2026-10-10 批准的路线 A）。
> 它是**占位资产**，目的是让生成模块不被美术阻塞；**正式美术后续按同一规格替换**，生成代码不动。

### 16.1 为什么先做灰盒

生成模块要的是三层产物：① 瓦片 ② **房间块 prefab** ③ 主题套系。
现成素材包只能解决 ① —— **② 才是工量大头**，且必须按 §4.3 的接口规格排布，任何素材包都不会提供。
所以先用代码把 ② 打通：瓦片由代码画、房间块由代码按规格拼装，**生成模块当天就能跑通 A1~A13**。

### 16.2 瓦片规格（**已冻结，正式美术沿用**）

| 项 | 值 | 理由 |
| --- | --- | --- |
| 像素尺寸 | **64 × 64** | 与工程既有 `Assets/Art/PNG/Grass_*map001.png`（实测 64×64）一致 |
| `spritePixelsPerUnit` | **64** | 1 瓦片 = 1 世界单位，房间块尺寸与生成网格才对得上 |
| `filterMode` | **Point** | 像素风，绝不能被双线性糊掉 |
| mipmap / 压缩 / 尺寸上限 | 关 / **Uncompressed** / 128 | 占位图是纯色块，压缩只会引入杂色；128 上限可挡住"误放一张 2048 大图" |

每主题 4 张瓦片：`Tile_Fill`（实心，`ColliderType.Grid`）、`Tile_Top`（顶面亮边，站得住的"面"）、
`Tile_Beam`（平台/立柱，可站）、`Tile_Deco`（背景装饰层，**无碰撞**）。

### 16.3 三套主题（= 三个空间层，一眼可辨）

| 主题 Key | 中文 | `MapLayer` | 配色取向 |
| --- | --- | --- | --- |
| `Underground` | 地下 | 1 | 冷灰蓝岩（Fill 暗、Top 略亮） |
| `Surface` | 地表 | 2 | 土棕底 + 草绿顶 |
| `Building` | 地表建筑 | 3 | 砖红木色 |

用途：① 让"层"在画面上可辨（§9 U2/U3 的可读性要求）；② 作为 `MapBiome.artThemeId` 的落地起点。

### 16.4 房间块规格与已产出清单

**块 = 40 × 24 格**（= 2560 × 1536 px @64px）= 1 个布局格。
地板行 0~2（第 2 行用 `Tile_Top`）、天花板行 22~23、左右墙各 2 格厚；
**横向出口 = 墙上挖 4 格高的洞，洞底 = 档位地板行**（§4.3 C7）；
**竖直开口 = 第 19~21 列（中心 `ShaftColumn = 20`）把天花板 / 地板挖通**，上下接口用**同列**匹配（§4.4 C10.6）。

> ⚠️ **规格 v2（2026-10-10 修订）：每个房间都带 L/R/U/D 四向接口，未使用的开口由运行时封堵（Pass E）。**
> 原因是实测撞出来的：只做左右门时，"支路"只能和主路挤在同一条横排上，**2D 网格里必然重叠** ——
> 竖直开口是"支路能挂在主路正上方"和"跨层能成立"的前提。代价是装配阶段必须补一步"封口"。

每主题 6 型（命名 `Chunk_{Theme}_{Type}`）：

| Type | `chunkType` | 接口（v2 四向） | 横向高度档 | 内容 |
| --- | --- | --- | --- | --- |
| `Entry` | 1 | `Socket_R` + `Socket_U` | 0 | 起点位（1 个标记点）；**不向下开口**（它是最下面的起点房） |
| `Corridor` | 2 | `L` + `R` + `U` + `D` | 0 | 两根立柱 + 1 个标记点 |
| `Combat` | 3 | `L` + `R` + `U` + `D` | 0 | 3 段平台 + 3 个标记点（2 敌人 + 1 精英） |
| `DeadEnd` | 11 | `L` + `U` + `D` | 0 | 1 个宝箱位 |
| `LayerLink_Stair` | 9 | `U` + `D`（同列 20，**无侧门**） | —（竖直不看档位） | 竖井 + 6 段交错平台 |
| `BossGate` | 10 | `L`（档 0，玩家从地面走进来）+ `R`（`socketType=3` boss 门，**不挖洞**，档 1）+ `U` + `D` | 0 / 1 | 台阶登到档 1 + boss 位 |

prefab 结构 = §4.3 规范，实测含：
`Grid` / `Tilemap_Deco` / `Tilemap_Ground`（`Rigidbody2D(Static)` + `CompositeCollider2D(Polygons)` + `TilemapCollider2D`）/ `Socket_*` / `SpawnSlot_NN` / `CameraBounds`（trigger）/ `RoomMarker`。

### 16.5 坐标与命名约定（**程序可直接依赖**）

| 项 | 约定 |

| 接口坐标 | 门洞**中心** = `(x, 地板行 + 2)`；`Socket_L` 在 `x = 0.5`，`Socket_R` 在 `x = 39.5` |
| 竖井接口 | `Socket_D` 在 `(20.5, 0.5)`、`Socket_U` 在 `(20.5, 23.5)` —— **必须同列**（C10.6） |

| 块根节点 | `Chunk_{Theme}_{Type}`；`MapChunk.prefabPath` = `Prefabs/RunMap/Placeholder/{Theme}/Chunk_{Theme}_{Type}`（正式资产替换后改前缀即可） |

**④ 房间内部地形起伏 + 一条被抓出来的真缺陷**（2026-10-10 续）
