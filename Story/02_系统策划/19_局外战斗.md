## 3. 二选一：(A) 门客模拟战 vs (B) 推迟并入局内

| 维度 | **(A) 门客模拟战** | **(B) 推迟 + 并入局内（✅ 采用）** |
| --- | --- | --- |
| 要做什么 | 局外选 1~2 门客 vs 敌方模板 → 自动结算 → 胜/负 + 奖励/重伤 | 不写新系统；局外冲突由"派遣进局"承接 |
| 前置依赖 | 需要一个**"为什么打"的玩法**（护送/运送） | 无 |
| 新增代码 | 战斗结算器 + 选人 UI + 结果面板 + 奖励发放 | **0** |
| 新增表 | 可零新表（常量/复用 `Retainer`），但要新增**规则** | 0 |
| 可验证性 | 只能验证"公式算得对"，**验证不了玩法** | 现有派遣/局内链路已验收 |
| 与既有规则冲突 | 与局内的战斗规则**分叉**（概念案要求"同一套角色逻辑"） | 无冲突 |
| 工作量/风险 | 中（UI+结算+平衡）；易反复改 | **0** |
| 用户优先级 | 2/2、第二阶段 | 同 |

**采用 (B)。**

## 4. 为什么推迟（**5 条理由**）

| # | 理由 | 证据 |
| --- | --- | --- |
| **R1** | **宿主玩法不存在**：M6 的定义是"护送等局外冲突"，而 M5 本轮**只做资源↔物品兑换**，**没有运送/护送**（无发货、无路线、无时长、无失败率） | `18_市场.md` §1.2 N3；概念案 §6 M5 原话 |
| **R2** | **会变成第二套战斗规则**：局内已有 `PlayerHealth` / `AllyController` / `EnemyPlaceholder` / 门客 HP（W3.3）/ 扎营补员；再做"攻击-防御/2、30 回合"的纯 AI 结算 = 两套数值与体感，日后必然分叉 | 概念案硬约束「所有角色走同一套角色逻辑」；`15_门客生命与阵亡.md` |
| **R3** | **验证不了真实体验**：纯 AI 模拟战只能验"公式对不对"，验不了护送/路线/失败率；用户要的是"**能验证的最小闭环**"，而这个闭环要等运送 | 计划文档 W5 口径 |
| **R4** | **优先级最低且是第二阶段**：概念案把 M5/M6 列为**后置**、优先级 2/2；W5 已排 M4 事件、M14 地形阵营、M5 市场，M6 挤进来会拖住收尾 | 概念案 §6；`04_功能开发计划与优先级.md` 优先级表 |
| **R5** | **"局外冲突"的体验已有承接**：玩家想要的"不带进局内也能打的冲突"，当前由「**派遣 → 就地进局内战斗**」承接（W2/W3 已验收），不需要第二个战斗系统 | `09_派遣与编队.md`、W3 验收报告 `82c4032` |

> **一句话**：**没有护送，就没有局外战斗；有战斗，就必须和局内同一套规则 —— 而现在该做的，是把局内那一套继续做厚。**

## 6. 附录：**若将来做 (A) 的最小方案**（不在本轮范围，先留着免得重设计）

| 项 | 方案 |
| --- | --- |
| 参战 | 局外选 **1~2 名门客**（`Retainer` 表 `Hp/Attack/Defense/Speed`，已存在） |
| 敌方 | **零新表**：先用 **2 个常量模板**（弱/强），或直接复用 `Retainer` 表某几行当"敌方门客" |
| 结算公式 | 先手 = `Speed` 高者（相同则门客先手）；每回合：`伤害 = max(1, Round(攻击 − 防御 / 2))`；`HP = Retainer.Hp`（受伤累计）；**回合上限 30**，达到上限则**剩余 HP 百分比高者胜**（平局判门客小败） |
| 结果 | 胜 → 发放资源奖励（常量）；负 → 参战门客 `RetainerService.Wound(id, 30)`（**不死亡**） |
| 表需求 | **可零新表**；若要内容化，再考虑 `Enemy` 模板表（`Index/NameKey/Hp/Attack/Defense/Speed/…`），用现有 12 类型即可 |
| 最小验收（若做） | ① 能选 1~2 门客 ② 结算出胜/负 ③ 伤害可手算复现 ④ 败者重伤 30s ⑤ **不进入局内场景**（纯面板） |
