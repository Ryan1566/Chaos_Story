# 策划文档模板使用说明

> 状态：草稿
> Owner：策划
> 最后更新：2026-10-05
> 关联：`Story/README.md`、`Story/01_企划/00_企划文档模板.md`、`Story/02_系统策划/00_系统设计文档模板.md`、`Story/03_配置表设计/02_配置表字段规格模板.md`、`Story/03_配置表设计/01_配置表填写规范.md`

## 1. 三份模板分别在什么时候用

| 模板 | 位置 | 什么时候写 | 回答的问题 | 对应产出 |
| --- | --- | --- | --- | --- |
| **企划文档模板** | `Story/01_企划/00_企划文档模板.md` | 需求刚拿到手、还只有"想法"时 | 这是个什么游戏？玩家图什么？**做多大范围？** | 需求的口径统一 |
| **系统设计文档模板** | `Story/02_系统策划/00_系统设计文档模板.md` | 某个模块决定要做了（企划第 6 节排过优先级） | 这个系统的**规则、数值、状态、异常**是什么？ | 程序能照着实现、验收能照着测 |
| **配置表字段规格模板** | `Story/03_配置表设计/02_配置表字段规格模板.md` | 系统设计里出现了"需要策划填的数据" | 这张表的**每个字段**叫什么、什么类型、什么取值？ | 一份能直接照着填的 `xlsx` |

### 三者的关系（不要跳步）

```
企划（为什么做、做多大）
   └─► 系统设计（怎么做、规则是什么）
          └─► 配置表字段规格（哪些数字要策划填、字段长什么样）
                 └─► xlsx 源表（真正被导出成 Json / C# 的东西）
```

- **只写企划不写系统设计** → 程序问「血条怎么算」时无据可依，会返工。
- **只写系统设计不写字段规格** → 直接开 Excel，必然出现「字段名拼错 / 类型选错 / 少了字段」。
- **字段规格与 xlsx 不一致** → 以**字段规格为准**，改 xlsx；两份必须同一天更新。

## 2. 元信息块与状态流转（每份文档都必须有）

所有文档头部必须有：

```markdown
> 状态：草稿 / 评审中 / 已定稿 / 已实现
> Owner：策划 | 架构师 | 程序
> 最后更新：YYYY-MM-DD
> 关联：<相关文档或配置表路径>
```

| 状态 | 含义 | 谁能改成下一个状态 |
| --- | --- | --- |
| 草稿 | 还在写，别人**不要**照着实现 | 作者自己 |
| 评审中 | 写完了，等架构师/程序提异议 | 作者 → 评审人 |
| 已定稿 | 语义冻结，程序可以依赖 | 评审通过后由作者改 |
| 已实现 | 程序已按它落地并通过验收 | 程序回填 |

**定稿后不要再改语义**。确需修改：把状态改回 `评审中`，并在文档末尾的「变更记录」里写清改了哪一条，
否则代码实现会和文档对不上。

### 路径写法

文档之间一律用**仓库相对路径**。**基准是 `Chaos_Story` 仓库根（`Assets/Chaos_Story/`）**，例：

```
Story/03_配置表设计/01_配置表填写规范.md
Story/01_企划/01_核心循环.md
```

> **两套基准要分清**（2026-10-05 起 `Story/` 已是独立仓库 `Chaos_Story`）：
> - **`Story/` 内部的文档互相引用** → 以 **`Chaos_Story` 仓库根**为基准，写成 `Story/…`。
>   （这与迁移前"以主仓库 `Assets/` 为基准"的写法**字面完全一致**，所以既有引用无需改写。）
> - **引用主仓库（Unity 工程）里的东西**（配置表源表、`Scripts/`、`Learn/` 等）→ 以**主仓库 `Assets/`** 为基准，
>   写成 `Excel/Chaos_excel/Item_道具表.xlsx`、`Scripts/Runtime/...` 这种形式。
>
> 不要写 `D:\...` 绝对路径。

### 版本控制

- `Story/` 是**独立 git 仓库 `Chaos_Story`**（仓库根 `Assets/Chaos_Story/`，
  remote `git@github.com:Ryan1566/Chaos_Story.git`，分支 `main`）。文档已提交并推送。
- 文档改动请在**该仓库内单独提交**：`git -C Assets/Chaos_Story add … && git -C Assets/Chaos_Story commit -m "…"`，
  **不要与主仓库的代码改动混在同一个提交里**。
- 提交前请先征询 **Lead**。

## 3. 从"用户口述需求"到"合规 xlsx"的完整流程

```
① 用户口述需求
      │
② 策划：写 Story/01_企划/NN_*.md（企划文档模板）
      │   └─ 用户对第 7 节「数值框架」、第 3 节「目标平台」的确认至关重要
      │
③ 策划：对 MVP 范围内的模块，逐个写 Story/02_系统策划/NN_系统.md（系统设计文档模板）
      │   └─ 重点：第 3 节规则、第 4 节公式、第 7 节「本系统需要的字段」
      │
④ 策划：把第 7 节里的字段落成 Story/03_配置表设计/NN_表名_字段规格.md（字段规格模板）
      │   └─ 同时在 Story/03_配置表设计/00_配置表清单.md 登记一行
      │
⑤ 策划：照着字段规格 + 01_配置表填写规范.md，在 Excel/Chaos_excel/ 填 xlsx
      │   └─ 过一遍规范 §9 的 12 项自检清单
      │
⑥ 架构师：落地方案评审（Story/04_架构/）
      │
⑦ 程序：执行导出菜单，接业务逻辑（Story/05_程序/）
```

**硬性闸门**（见 `Story/README.md` §4）：程序只有在「策划文档已定稿」**且**「架构师落地方案已定稿」
之后才动手写业务逻辑。所以**第 ②③④ 步要尽量一次写到位**，写到能支撑 MVP 的粒度即可，不要追求完整。

## 4. 各模板的填写要点速查

### 4.1 企划文档模板 —— 三个必答问题

| 章节 | 一句话要求 | 最容易糊弄的地方 |
| --- | --- | --- |
| §1 一句话概述 | 能被复述给第三个人听懂 | 写成宣传语（"史诗级体验"） |
| §2.2 Non-goals | 明确本期**不做**什么 | 整节留空 → 范围必然失控 |
| §5 核心循环 | 玩家重复做的动作序列 + 驱动力 | 只写"战斗→升级"，没写为什么还想再来一次 |
| §7 数值框架 | 口径 + 单位 + 上限 + 取整 | 不写单位，导致配置表里毫秒/秒混用 |

### 4.2 系统设计文档模板 —— 四个必答问题

| 章节 | 一句话要求 |
| --- | --- |
| §3 规则详述 | 每条规则可判定、有编号、能写测试用例 |
| §4 数值与公式 | 每个数字都必须写清"来源：硬编码还是哪张表的哪一列" |
| §7.2 需要的字段 | 直接对应配置表列，且**类型只能从 12 个白名单里选**（见 §5 第 1 条） |
| §9 边界与异常 | 至少覆盖：缺 ID、数值为 0、达到上限、重复操作、旧存档 |

### 4.3 配置表字段规格模板 —— 三个必答问题

| 章节 | 一句话要求 |
| --- | --- |
| §3 字段清单 | 每个字段的「含义与取值」必须写**范围 + 量纲** |
| §4 枚举对照表 | 导出器不支持 enum，所有枚举/开关的数字含义必须在这里手写清楚 |
| §9 待确认问题 | 还没定的数值不许空着，填 `0` 并在这里登记 |

## 5. 你必须知道的六条工程约束（会直接影响文档怎么写）

> 摘自 `Story/03_配置表设计/01_配置表填写规范.md`，完整版见该文件。

1. **类型白名单 = 12 个**（权威是 `ConfigManager.Convert` 的 `case` 列表，**不是任何文档**）：
   `int` `uint` `long` `ulong` `byte` `sbyte` `short` `ushort` `float` `double` `bool` `string`。
   - **"是/否"直接用 `bool`**：可填 `true`/`false`、`1`/`0`、`是`/`否`（不区分大小写），**不能留空**——
     填别的会抛异常并**中断整批导出**（规范 §3.3）。
   - **`enum` 仍不支持**：枚举设计成 `uint`（或 `byte`/`short`）+ 数字对照表，不要用布尔或字符串代替。
   - **禁止**：`enum` / `DateTime` / `decimal`（`JsonUtility` 会**静默丢弃**）/ `char`（JSON 存数字），
     以及已被删除的 `int32` / `int64` / `long long`（现在填了会在导出阶段直接报错）。
2. **一张表 = 一个页签 = 一个平铺的二维表**。导出器**不支持嵌套结构**（数组里套数组）。
   需要"一个技能挂多个效果"时，必须拆成两张表 + 外键，而不是在一格里塞 JSON。
3. **第 5 行 `server` 的列会被整列丢弃**；留空更危险（字段在类里、值不在 Json 里）。
   设计字段时就要决定这一列"客户端要不要"。（2026-10-05 Lead 已裁决：这是**正式功能**，不是缺陷。）
4. **第 7 行就是第一条正式数据**（不是示例行）。（同上，已裁决，不改导出器。）
5. **字符串不能含英文逗号 `,`、英文双引号 `"`、换行**。
6. **源表目录里只允许放成品表**（表头齐全 + 第 7 行起有正式数据）。实测（Lead 2026-10-05）：
   **页签完全空白** → `Dimension == null` → 抛 `NullReferenceException` → **中断整批导出**（该表及其后所有表都不导出，有 error 日志）；
   **只有表头无数据** → 不抛异常，只在本表日志里留一条「该表无任何导出项」。
   未完成的表一律先移出 `Excel/Chaos_excel/`。是确凿缺陷，待架构师排期修复（详见规范 §7.1）。

任何一条想突破，都需要**程序先改导出器**——不要在设计文档里假设它已经支持。
唯一例外是第 6 条：它已被确认为缺陷、排期修复中，在修复前**按硬规则遵守**。

> **共享契约基准**：`Story/README.md`（Lead 已于 2026-10-05 复核更正第 5 行 / 第 7 行 / 菜单路径三处）。

## 6. 一份策划文档的完成标准（Definition of Done）

写完自检，全部为「是」才算完成：

- [ ] 有元信息块，`状态`/`Owner`/`最后更新`/`关联` 四项齐全，路径以 **`Chaos_Story` 仓库根**为基准（主仓库对象除外，见 §2「路径写法」）。
- [ ] 文件名符合 `NN_主题.md`，序号在本目录内唯一。
- [ ] 没有 `⬜` 残留；没定的内容写成"待确认"并**进了文末「待确认问题」表**。
- [ ] 「待确认问题」表里每条都写了**卡住了什么**和**需要谁确认**。
- [ ] 涉及的数字都写了单位和取值范围。
- [ ] 涉及配置表的地方，写清了**表名 + 字段名 + 类型**，且类型在白名单内。
- [ ] 涉及"是/否"的地方用 `bool`（取值只能是 `true`/`false`、`1`/`0`、`是`/`否`，不能留空）；
      "枚举"仍用 `uint` + 数字对照表（**导出器不支持 `enum`**）。
- [ ] 没有使用 `decimal` / `char` / `int32` / `int64` / `long long` / `DateTime` 这些不可用类型。
- [ ] 「边界与异常」至少覆盖：数据缺失、数值为 0、达到上限、重复操作。
- [ ] 与既有文档没有语义冲突；若有冲突，已在文末「变更记录」或「待确认问题」里说明。
- [ ] 文末有「变更记录」。

## 7. 常见错误（写之前先看一遍）

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 把"是/否"设计成 `uint` 的 `0/1`（旧写法） | 多绕一层：`0/1` 没有语义，读表的人要回头查对照表 | **直接用 `bool` 列**（可填 `true`/`false`、`1`/`0`、`是`/`否`）；旧表的 `uint` 0/1 不必回改 |
| 在 `bool` 列填 `yes` / `no` / `开` / `关`，或留空 | `bool` 只认 6 种写法，其余**抛异常并中断整批导出** | 严格用 `true`/`false`、`1`/`0`、`是`/`否`，且**逐行填满** |
| 一个字段里塞多个值（`效果=攻击+10;防御+5`） | Json 里无法拆分，程序无法解析 | 拆成 `effect_type` + `effect_value`，或拆表 |
| 数值只写"适量""若干" | 程序无法实现，配置表无法填 | 给具体值或区间 + 待确认登记 |
| 文档写完了但清单没更新 | 索引与实际不符，后人找不到 | 每张表同步更新 `00_配置表清单.md` |
| 定稿文档直接改内容不留痕 | 代码实现与文档对不上 | 改回 `评审中` + 变更记录 |
| 用绝对路径引用文件 | 换机器/换目录就失效 | 用仓库相对路径：`Story/…`（基准 = `Chaos_Story` 仓库根）/ 主仓库对象用 `Assets/…`（见 §2） |
